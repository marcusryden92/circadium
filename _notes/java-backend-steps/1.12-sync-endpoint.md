## Design decisions (2026-11-22)

- **Shape.** Request `SyncRequest {changes: DatabaseChanges, clientKnownDataVersion}` from `wire.ts`; all 14 groups required. 200 `SyncResult {newDataVersion}`. Stale is a 409 ProblemDetail (`code: "stale"`, plus `freshState`, the `BootstrapPayload`), so every non-2xx answer from the API stays a ProblemDetail; springdoc documents it as `StaleSyncProblem`. The TS `{success, reason}` union is the 1.13 transport's job. Records live beside the bootstrap ones in `calendar/CalendarContracts`; the row records are shared by both directions, plus `SimpleEventRow`, `CategoryRow`, `QueueRow` for the stripped group rows.
- **Package `sync/`:** `SyncController`, `CalendarSyncService` (OCC + transaction), `CalendarChangeWriter` (the 14 handlers, TS order and per-handler operation order kept exactly), `BulkStatements` (SQL builder/executor), `StaleSyncException`.
- **`unnest` instead of `VALUES`.** One array parameter per column, expanded by `unnest(...) AS v(...)`: same single statement and the same ghost-id-safe, owner-scoped join, but a fixed parameter count. A `VALUES` list binds one parameter per cell, and Postgres caps a statement at 65,535 (the TS's planner update, 26 per row, hits it at ~2,500 rows). Proven by a 3,000-planner test (87,000 values).
- **Transaction.** `TransactionTemplate`, 60-second timeout (the web's), default READ COMMITTED like Prisma. The version bump runs first, so its row lock queues a concurrent sync for the same account, whose version check then fails. On zero rows the service ends the transaction and loads `freshState` through `CalendarBootstrapService.load` in a new one (resolves the 1.11 follow-up: `load` sets its isolation level, which must be a transaction's first statement). A deleted account answers 401 `account_not_found` from there.
- **Timestamps as the TS writes them.** `updatedAt` is the server's sync time in `toISOString()` form (three fractional digits) on every update and on engine-output creates; other creates keep the client's timestamps; engine-output `createdAt` is left to the column default `(now())::text`. The de-muddle cleanup stays out of this step (its own step after; see the plan's Deferred cleanups).
- **Ownership checks the TS lacks.** Rows read back through a parent, or holding a table-wide unique slot, may only reference the caller's own rows, else they are skipped: a time window's `categoryId` (create and update), a queue member's `queueId` (create and update) and `plannerId` (create), a dependency's two ends. Without it an account that knew another's ids could plant a window in their category or a member in their queue (bootstrap reads both through the parent), or occupy their planner's one queue slot or a dependency pair. Legitimate diffs never hit it, so the corpus is unaffected.
- **Validation.** Groups and their lists required, every row id `@NotNull`, weekday fields 0-6 (the TS fails on a template's out-of-range day too). Other required columns are left to their NOT NULL constraints (500, as the TS's `error`). Unknown fields are ignored, which matters: the engine's extended props carry runtime-only fields.
- **Jackson 3 rejects a missing primitive** (`FAIL_ON_NULL_FOR_PRIMITIVES` is on by default). The extended props' trespass flags are runtime-optional in the TS, so the record takes `Boolean` and the writer writes `false` for null, as the TS's `?? false` does. The corpus found this.
- **Engine message payloads** deserialize to their JSON text (`RawJsonDeserializer`, the inbound counterpart of `@JsonRawValue`) and are written `::jsonb`. Numbers may print differently from `JSON.stringify` (`-3.0E-7`), but the stored values are equal.
- **The stale log line** is fixed text: `ErrorResponseException`'s default message prints the ProblemDetail, which would put the user's whole calendar in the log.

## Golden corpus

- **Recorded from the real TS path.** `client/web/__tests__/contracts/captureSyncCorpus.test.ts` (`pnpm fixture:sync`, dev database up; skipped unless `CAPTURE_SYNC_CORPUS`): per scenario, reseeds a scratch database with `calendar/bootstrap-seed.sql` (shared with 1.11), edits `fetchFreshState`'s output the way the client would, diffs it with the shared `compareData`, sends it through `syncCalendarData` (auth mocked), and writes `server/src/test/resources/sync/corpus/<name>.json`: diff, version, response, and the rows afterwards from `sync/dump-state.sql`. The clock is frozen at `2026-03-02T06:00:00Z` (`Date` only, so Prisma's timers still run); the column default's `createdAt` becomes `<column default>`. The dump sorts with `COLLATE "C"`, since the Alpine dev image and the Debian test image collate differently.
- **12 scenarios:** planners + a category created in the same sync; a planner delete with its pruned links; events and extended props (the upsert keeping the old props id, a props row without trespass flags and with runtime-only fields); templates across weekdays and time windows; queues, members, dependencies; engine output (rewrites with empty engine timestamps, an awkward JSON payload); location rename and travel-time overrides; location delete (cascade and set-null); a hand-built diff aimed at the other account and at missing ids; empty diff; stale; **first regen**: 60 new tasks under a new goal plus a real `generateCalendar` run, 352 writes.
- **Replay:** `SyncCorpusIntegrationTest` (12 dynamic tests, clock frozen to the same instant): status and body (`freshState` compared in any array order), then the dump compared strictly. Each scenario must finish inside 10 s; the 352-write regen takes ~0.46 s including reseed and dump.
- **Behaviour:** `SyncIntegrationTest` (12): no token 401; deleted account 401; empty diff leaves the version; stale writes nothing and carries `freshState`; two concurrent syncs at one version give one 200 and one 409; missing group, null id, weekday 7 and missing version give 400; the ownership checks; 3,000 planners; the OpenAPI document.

## Follow-ups

- **1.13 transport mapping:** 200 → `{success: true}`, 409 → `{reason: "stale", freshState}`, any other HTTP answer → `{reason: "error"}` (the client snaps back), and only a failed fetch → throw (retry with backoff). A 5xx must not become a transport retry: a diff that broke a constraint fails the same way every time. Check the CORS preflight for a JSON `POST` from the web origin.
- **The web's own sync lacks the ownership checks.** Moot once 1.13 points the web at Java and Phase 2 deletes the server action; prod has one user.
- **No request-size cap.** The 60-second timeout bounds the work; a body limit would also bound memory. A cap low enough to matter risks rejecting a real large regen, which the client answers by discarding the user's edits, so size it from real traffic.
- **Carried from 1.11:** response compression (the 409 carries the whole calendar too); OpenAPI required/nullable markers (row ids are now marked required, the rest not).
- **Engine-row `createdAt` offset** follows the session time zone (PgJDBC sends the JVM's: UTC in the deployed image, the developer's locally). Nothing reads it; the de-muddle replaces it.
