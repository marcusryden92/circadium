# 2.2 Group B: categories, locations (Places/Routes + budget + top-up job), habits

**Status:** in progress (started 2026-11-24) · Phase 2 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** Move the second group of direct actions to Java. Categories turn out to be a deletion:
all 13 exports of `actions/categories.ts` are dead (the live category path is Redux + the OCC
diff sync end to end; the file is a pre-diff-sync CRUD surface that even drifted stale —
no `confineToOwnWindows`, non-serializable Map return). Locations move with the Google Places
(New) autocomplete/details and Routes `computeRouteMatrix` clients, the transactional
`TravelApiBudget` reservation and the freshness policy; the silent travel top-up becomes a
server-side `@Scheduled` + ShedLock job. Habits move wholesale (CRUD + the assistant's
`applyHabitChanges` batch). The habit tables' TEXT timestamps migrate to `timestamp(3)` with
their writes (the 1.13b per-group rule).

**DoD:** `.\mvnw.cmd verify` green with the new integration tests (Google clients faked);
`pnpm -r type-check && pnpm -r test && pnpm --filter web build` green;
`actions/{categories,locations,habits}.ts` and `lib/google-maps-api.ts` deleted; no Group B
write bumps `users.dataVersion`; migrations applied on dev Neon.

## Decisions (2026-11-24)

- **Dead surface is deleted, not ported.** `actions/categories.ts` entirely (13/13 dead — the
  categories page and the assistant both mutate Redux and ride the sync diff; `markSynced`
  was never even wired for categories). In `actions/locations.ts`, 11 of 21 exports are dead
  (reads superseded by the bootstrap, edits/deletes/overrides by the diff) and get no endpoints.
  `updateHabit` (standalone) has zero UI call sites — its semantics live on inside the batch.
- **`assignLocationToPlanner` / `setUseParentLocation` become pure Redux.** Both call sites
  (EventPopover, EditDrawer) already dispatch the same planner change into Redux, which the
  diff sync persists; the direct action was a redundant second write ("resolves as a no-op
  update against the already-written row"). Dropping the direct call leaves one write path.
- **Endpoints** (authenticated; in the `calendar` package per the per-domain-direct-action
  layout; none of them moves `users.dataVersion`):
  - `POST /locations/search` `{query, sessionToken?}` → predictions. Per-user in-memory
    throttle, 30/min (the TS limiter; single-instance like the auth rate limiter).
  - `POST /locations` `{name, placeId, sessionToken?}` → `SerializedLocation`. Max 5 locations
    (`location_limit`), duplicate placeId refused (`duplicate_place`), Places details fetched
    server-side.
  - `PATCH /locations/{id}` `{name?, placeId?, sessionToken?}` → `SerializedLocation`. A placeId
    change refetches details, refuses a duplicate, and deletes every travel-time row touching
    the location (re-bought on demand).
  - `POST /travel-times/fetch-missing` `{transportMode}` → `{fetched, skipped, failed,
    travelTimes}`; `POST /travel-times/refresh-all` `{transportMode}` → `{updated, failed,
    travelTimes}`. Both return the account's fresh rows so the client skips the follow-up
    read the TS flow needed (`fetchTravelTimes` dies with it). Budget refusal and the
    refresh-all gates answer 409 with the TS reason strings (code `travel_budget` /
    `refresh_gate`).
  - `defaultTransportMode` joins `PATCH /scheduling/preferences` (the Group A deferral).
  - `GET /habits` → `{buckets, habits, items}`; `POST /habits/buckets`, `PATCH
    /habits/buckets/{id}`, `DELETE /habits/buckets/{id}` (no-op safe); `POST /habits`,
    `DELETE /habits/{id}`; `PUT /habits/{habitId}/items` `{plannerId}` (returns the existing
    link when already tracked — the TS idempotency), `DELETE /habits/{habitId}/items?plannerId=`;
    `POST /habits/apply` — the assistant batch, one transaction, same order of operations and
    skip-unknown semantics, caller-supplied bucket/habit ids adopted, link adds validated
    against owned habits + trackable planners with `ON CONFLICT DO NOTHING`.
  - Trackability is the TS rule exactly: root row (`parentId` null) whose `recurrence` parses
    as JSON with `freq` in {daily, weekly, monthly} (`item_not_repeating` on violation).
- **Google clients** live in `external/maps` (deviation from the reference tree's
  `external/places/`: Routes is not Places; "Places" stays out of anything user-facing
  either way): `PlacesClient` + `RoutesClient` interfaces, Google impls on `RestClient` over
  `java.net.http.HttpClient` (the Pwned/Resend pattern), 3-attempt retry on 429/5xx with
  backoff, the same field masks (`id,formattedAddress,location`;
  `originIndex,destinationIndex,duration,distanceMeters,status,condition`), origin-grouped
  matrix requests, departure times = next Monday 08:00/14:00/23:00 UTC (the TS computed
  "local" on a UTC server, so UTC is the deployed behavior). `GOOGLE_MAPS_API_KEY` is
  optional in every profile (PostHog precedent): absent → the endpoints answer 503
  `maps_not_configured`, so the deploy is not coupled to a Fly secret. Tests replace both
  clients with fakes in `TestcontainersConfiguration` (`FakeBreachedPasswords` precedent).
- **The budget reservation gets the lock the TS never had.** `reserveElements` logic is ported
  verbatim (month-start UTC reset, cap 4500), but the Java reservation runs
  `SELECT … FOR UPDATE` on the `"global"` row inside the transaction — two concurrent
  fetches could both slip under the cap in the Prisma version (read-then-upsert under read
  committed). Stricter-than-TS is the 1.12 precedent.
- **The top-up becomes a nightly job and the client trigger dies.** `jobs/TravelTopUpJob`:
  `@Scheduled` (daily 03:40 UTC) + ShedLock (`shedlock` table via Prisma migration, the
  baseline rule's list). Per user with ≥2 locations: the per-user 24h `lastTravelTopUpAt`
  allowance, oldest-first stale rows capped at 10 pairs, quiet budget no-op — the TS
  semantics, just server-driven. CalendarProvider's once-per-load `topUpStaleTravelTimes`
  effect is removed; clients see fresh rows on the next bootstrap.
- **Habit timestamps migrate now**: `HabitBuckets`/`Habits` createdAt+updatedAt and
  `HabitItems` createdAt go TEXT → `timestamp(3)`; entities flip `String → Instant`; the wire
  stays ISO strings; Java stamps both timestamps itself (no triggers, the UserViewStates
  pattern). `types/prisma.ts` re-declares them `string` (the calendar-tables pattern).
- **Parity evidence:** integration tests pin the TS actions' DB effects and response shapes —
  location caps/dedup/cascades, TTL + unroutable-retry filtering, budget refusal/reset,
  refresh-all gates, custom-override preservation, habit batch order/skip/adopt semantics,
  no-dataVersion-move everywhere. Policy functions get direct unit tests (ported thresholds).
  Same deviation as 2.1 on the group loop's "bake before delete": flip and deletion land
  together; rollback is git revert.

**Deploy note:** `GOOGLE_MAPS_API_KEY` must be set as a Fly secret on `circadium-server-staging`
and `circadium-server` for location/travel features to answer; until then those endpoints
return 503 `maps_not_configured`. Migration rides the Vercel build as usual (the 1.13b dance).
