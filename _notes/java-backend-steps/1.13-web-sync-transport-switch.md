# 1.13 Web sync transport switch

**Status:** ◐ On Java in prod since 2026-11-22; the prod browser check, the bake and the deletion pass to go · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** swap the 0.8 transport for the Java fetch behind an env flag; staging bake → prod.

**DoD:** web in production on Java sync; forced-stale via a second session recovers via `adoptFreshServerState`; the old action path deleted after bake.

**See also:** the seam being swapped is the transport injected in [0.8](0.8-sync-extraction.md) (`useCalendarServerSync`).

## Decisions (2026-11-22)

- **Order: this step before the timestamp de-muddle.** The de-muddle then changes only the shared diff, the Java writer and a Prisma migration, not the 14 TS handlers this step deletes. Cost: the TS reference for recapturing the sync corpus goes with them, so after the deletion the Java tests are the reference (the corpus files stay as Java test resources).
- **The initial load moves too, under the same flag.** `useFetchCalendarData` reads `GET /calendar/bootstrap` instead of the `fetchCalendarData` action. No Phase 2 group owns that action and 2.6 needs it gone; load and stale recovery now read the same Java snapshot. The bootstrap's `locations` and `travelTimes` are ignored on load: `UserProvider` still loads them with the scheduling settings (`fetchAllSchedulingData`, Group B).
- **One flag, `NEXT_PUBLIC_CALENDAR_BACKEND`** (`client/web/lib/calendarBackend.ts`): `java` sends load and sync to Java; unset (or anything else) keeps the server actions. Unset is the default so the prod merge changes nothing until the variable is set, separating the flip from the merge (which also carries 1.10b-1.12). Next inlines it at build time: flipping or rolling back is an env change plus a redeploy. `client/web/.env.local` sets `java`, so `pnpm dev` exercises the new path.
- **Transport mapping** (`client/web/lib/api/calendar.ts`, `syncCalendarChanges`): 200 → `{success: true}`; 409 `code: "stale"` with a `freshState` object → `{reason: "stale"}`; any other answer (400, 401 after the refresh-and-retry, 404, 500, a 409 without `freshState`) → `{reason: "error"}`, the client snaps back; no answer at all, a **502/503/504**, or a non-API error → throw, the sync loop retries with backoff. The gateway statuses are the proxy's, not the app's (the request may never have reached it), and a retry is always safe: a sync that did commit has moved the version on, so its replay comes back stale and adopts the committed state. A 500 stays a rejection: a diff that broke a constraint fails the same way every time.
- **`ApiError.problem`** keeps the whole parsed error body (empty unless it was a JSON object), since `freshState` is an extension member the standard fields dropped.
- **No phantom diffs from the switch.** The diff compares rows key by key (`objectsAreEqual`), not by key order, and 1.11's fixture test (`NON_EXTENSIBLE`) holds Java to the same key set as the web's own fetcher. The per-group `JSON.stringify` gate can still fire once after a regen reorders an array; the resulting diff is empty and answers 200 without a version bump, as before.
- **Response compression** (`server.compression`): JSON and `application/problem+json` over 2 KB, gzip. The 409 is `application/problem+json`, which Spring's default list leaves out (checked: dropping it fails the test). BREACH needs attacker-chosen input reflected beside a secret in one body; tokens travel in cookies, and the mobile token pair answers a request carrying only credentials or a refresh token. `ResponseCompressionIntegrationTest` (3, real port, real token): bootstrap gzipped with `Accept-Encoding: gzip`, plain without, the stale 409 gzipped.
- **CORS** already allows `POST` with `Content-Type` from the web origin (`CorsConfig`), so the JSON preflight needs no change; it is first exercised from a browser on staging.
