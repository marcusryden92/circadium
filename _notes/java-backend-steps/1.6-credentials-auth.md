### API

| Endpoint | Body | Responses |
|---|---|---|
| `POST /auth/register` | `name`, `email`, `password` (8+ chars, ≤72 bytes) | 202 `{status: VERIFICATION_EMAIL_SENT}` for new and taken emails alike; 400 validation |
| `POST /auth/login` | `email`, `password` | 200 `{status: AUTHENTICATED, tokens}` / `{status: TWO_FACTOR_REQUIRED}` / `{status: EMAIL_VERIFICATION_SENT}`; 401; 429 |
| `POST /auth/2fa` | `email`, `password`, `code` (6 digits) | as login; a wrong code is a 401 that counts toward lockout |

`tokens` is the same shape `/auth/refresh` returns. All 200s carry `Cache-Control: no-store`.

### What was built

- **Schema** (Prisma migration `add_audit_log_and_auth_lockouts`): `audit_log` (event, userId FK cascade, presented email, ip, user agent, detail, createdAt) and `auth_lockouts` (key, failedAttempts, lastFailedAt, lockedUntil).
- **`auth/CredentialsAuthService`** + **`CredentialsController`**: port of `actions/login.ts` / `register.ts`. Check order: lockout → account lookup → password → verified → 2FA. Unknown accounts still run a bcrypt check against a dummy hash (equal timing). Lookup is case-insensitive (NextAuth rows kept the typed casing); new registrations store the email lowercased.
- **`auth/AccountTokens`**: 2FA codes (6 digits, 5 min, one per email, constant-time compare, deleted on use) and verification tokens (uuid, 1 h), in the existing `TwoFactorToken` / `VerificationToken` tables.
- **`auth/LoginThrottle`**: per-email lockout via one atomic upsert (JdbcTemplate). 1–4 failures free, then 1, 2, 4 … 60 min; failures older than 24 h are forgotten.
- **`auth/RateLimitFilter`**: per-IP Bucket4j buckets (login + 2fa 10/min, register 5/h, refresh + logout 60/min), in memory, before Spring Security; 429 ProblemDetail with `Retry-After` and `requestId`.
- **`auth/AuditLogger`** (`REQUIRES_NEW`) + `AuditEvent`: REGISTER, REGISTER_DUPLICATE, LOGIN_SUCCESS, LOGIN_FAILURE (reason in `detail`), LOGIN_BLOCKED, LOGIN_UNVERIFIED, ACCOUNT_LOCKED, TWO_FACTOR_CHALLENGE, REFRESH_TOKEN_REUSE, LOGOUT.
- **`external/mail/AccountMailer`** interface + `LoggingAccountMailer` (logs the token under `local`, only "dropped" elsewhere).
- **`persistence/DbTime`**: shared UTC/millisecond conversion; `TokenService`, `AuditLogger`, `LoginThrottle`, `AccountTokens` use it.
- `auth/PasswordConfig`: `BCryptPasswordEncoder(10)`.

### Design decisions

- **`/auth/2fa` re-checks the password.** The code is never the only factor between a guesser and the account, and wrong codes feed the same lockout.
- **No `TwoFactorConfirmation` rows.** That table bridged NextAuth's action → `signIn` callback; Java verifies the code and issues tokens in one request, so there is nothing to bridge. It stays in the schema for the web app until NextAuth is gone.
- **Registration does not reveal taken emails.** Same 202 either way; the duplicate is only audited.
- **New-password minimum is 8**, not the web form's 6 (ASVS). Login accepts any length so existing 6-character passwords still work.
- **Audit rows cascade-delete with the user** (account deletion removes personal data); failed attempts against unknown emails have no user and are kept.

### Follow-ups

- Fly runs **two** machines for staging. Rate-limit buckets are in memory per machine, so with both awake the effective per-IP limit doubles. Either `fly scale count 1` (matches the single-instance baseline) or move buckets to a shared store before relying on the limits.

- Resend delivery (1.7) replaces `LoggingAccountMailer`. Until then staging/prod drop verification and 2FA mail, so **registration and 2FA logins cannot complete on staging**; verified non-2FA accounts log in fine. 1.7 should also send a "you already have an account" email on duplicate registration.
- The rate-limit buckets are per instance; a second instance needs a shared store (Bucket4j has Postgres and Redis backends).
- `findFirstByEmailIgnoreCase` compares `upper(email)` without an index. Fine at current size; add an expression index (or normalize stored emails) once Flyway owns the schema.
- Audit-log retention/cleanup job, alongside the session cleanup job (Phase 2).
