# 2.1 Group A: occurrenceCompletions, viewState, scheduling settings/preferences

**Status:** ☑ DONE 2026-11-24 (code + gates; staging/prod deploy rides the next push) · Phase 2 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** Move the first group of direct actions to Java: the occurrence-completion log
(`actions/occurrenceCompletions.ts`), the canvas view state (`actions/viewState.ts`) and the
scheduling preferences (`actions/scheduling.ts`). Implement the Java endpoints, prove parity with
integration tests that pin the Prisma actions' exact DB effects and response shapes, switch the
web's call sites to `lib/api`, and delete the three action files. Low risk by design — this group
proves the per-group loop for B/C/D.

**DoD:** `.\mvnw.cmd verify` green with the new integration tests; `pnpm -r type-check && pnpm -r
test && pnpm --filter web build` green; the three action files deleted; no Group A write bumps
`users.dataVersion`; the migration applied on dev Neon.

## Decisions (2026-11-24)

- **The scheduling-settings initial load moves into the bootstrap.** `fetchAllSchedulingData`
  seeded preferences + locations + travel times from Prisma while the Java bootstrap already
  carried locations/travelTimes that the client deliberately ignored on initial load (the 1.13
  dual-sourcing note). `BootstrapPayload` gains `schedulingPreferences {bufferTimeMinutes,
  defaultTransportMode, weekStartDay}` (TS + Java), `useFetchCalendarData` seeds the
  schedulingSettings slice from it, and `UserProvider`'s scheduling fetch is deleted. One initial
  load, one source, one fewer cold-start roundtrip. The stale-adoption path adopts preferences the
  same way it already adopts locations/travelTimes.
- **`initializeState` takes locations/travelTimes as parameters.** The `locationsAtInitRef`
  mirror existed only because UserProvider's scheduling fetch raced the calendar fetch. With the
  bootstrap as the single source, the baselines seed from the same payload as the slices and the
  race note in `useCalendarServerSync` dies.
- **The missing-row preference fallback stays `bufferTimeMinutes: 5`.** The retired action fell
  back to 5 while the schema default (applied once any preference write creates the row) is 10.
  Parity preserves the quirk exactly: bootstrap answers 5/DRIVING/1 with no row; a weekStartDay-only
  create materializes buffer 10, as Prisma did. Logged under debt: normalize the two defaults
  post-cutover.
- **Dead TS surface is not ported.** `fetchUserSchedulingPreferences`, `fetchTaskPreferences` and
  `upsertTaskPreferences` have zero call sites; they die with `actions/scheduling.ts` and get no
  Java endpoints. The `TaskPreferences` table and entity stay for the 2.6 disposition.
  `defaultTransportMode` writes live in `actions/locations.ts` (`updateDefaultTransportMode`) and
  move with Group B.
- **`HabitCompletions.createdAt` migrates TEXT → timestamp(3)** — the one straggler 1.13b
  deferred to exactly this step. Prisma migration `habit_completions_created_at_timestamp`, same
  `USING "createdAt"::timestamp(3)` cast as 1.13b; entity flips `String → Instant`; the wire stays
  the ISO `...000Z` string (`CalendarContracts.iso`). `start`/`end` stay TEXT — domain datetimes
  ride the 2.5 decision point with `SimpleEvent.start`/`end`. No DB default and no trigger: Java
  stamps createdAt on create and never touches it on the upsert's update branch, as the TS upsert
  did. GDPR export/import tolerate the type change (export serializes Date → ISO; import's
  `createMany` accepts ISO strings for DateTime).
- **Endpoints** (all authenticated, no SecurityConfig change; CORS already allows
  PUT/PATCH/DELETE):
  - `GET /calendar/occurrence-completions` → the caller's rows (contract `OccurrenceCompletion`,
    all strings on the wire).
  - `PUT /calendar/occurrence-completions` `{plannerId, occurrenceKey, start, end}` → the row.
    404 `item_not_found` unless the planner is the caller's own (the TS "Item not found" check).
    One atomic `INSERT … ON CONFLICT ("plannerId","occurrenceKey") DO UPDATE SET "start","end"`,
    preserving id + createdAt on the update branch.
  - `DELETE /calendar/occurrence-completions?plannerId=&occurrenceKey=` → 204, a missing row is a
    no-op (the TS deleteMany semantics).
  - `GET /view-state` → `{graph, mindmap}` (nulls for a missing row); `PUT /view-state`
    `{kind: graph|mindmap, state: string|null}` → 204, patching only the named column
    (`INSERT … ON CONFLICT ("userId") DO UPDATE` on that column + `updatedAt`, which has no DB
    trigger — Java stamps it, as Prisma's `@updatedAt` did).
  - `PATCH /scheduling/preferences` `{bufferTimeMinutes?, weekStartDay?}` (at least one; weekday
    0–6 validated as the TS did) → 200 with the row's `{bufferTimeMinutes, defaultTransportMode,
    weekStartDay}` (non-empty body so the settings card's undefined-means-failed signal works).
    Create uses schema defaults for omitted columns, exactly matching the two Prisma upserts.
- **None of these writes bump `users.dataVersion`** — the out-of-band invariant the TS actions
  documented; asserted in the integration tests.
- **Parity evidence:** the TS reference actions are pinned by Java integration tests asserting
  column-level DB effects (upsert create/update branches, scoping, no-op deletes, defaults) and
  response shapes, plus the updated bootstrap golden fixture. The deviation from the group loop's
  "bake before delete": the web flip and the action deletion land together (full-phase run,
  2026-11-24); rollback is git revert of the flip commit.
- **Fixture updates:** `bootstrap-seed.sql` gains UserSchedulingPreferences rows for both seed
  accounts (the other account's row must not leak); `bootstrap-expected.json` and the recorded
  `freshState` in `sync/corpus/11-stale.json` gain `schedulingPreferences` (both compare
  NON_EXTENSIBLE); `db/schema.sql` mirrors the createdAt migration.

**Deploy order note:** the Prisma migration rides the web's Vercel build; the Fly deploy's schema
validate fails until it has run (the known 1.13b dance) — re-run the server job after the web
build if the race is lost.

- Two traps found by the first verify run, for the record:
  - `UserSchedulingPreferences` has **no FK to users** (NextAuth-era shape), so user-delete test
    cleanups never cascade to it — the seed now clears its own prefs rows and the preferences test
    cleans up explicitly. Anyone adding per-user rows to that table must do the same.
  - The machine's disk filled mid-verify (Windows pagefile ballooned under Docker + Maven + Node;
    Testcontainers Postgres then failed to start and the WSL disk went read-only). Recovery:
    delete leaked containers via vhdx reclaim, `pnpm store prune` (+2 GB), `npm cache clean`
    (+1 GB). Keep verify single and foreground, nothing heavy beside it.
