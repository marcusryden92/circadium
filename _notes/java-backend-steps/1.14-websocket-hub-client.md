**Task:** `/ws` authenticated at handshake (access JWT); per-user session registry **behind an interface** (single-instance impl now, Redis pub/sub impl slot documented); every successful sync publishes `{type:"dataVersion", value}` to the user's other sessions; a behind client runs the existing stale-adoption path. Client: reconnecting-WS module in `client/shared/src/sync/` (backoff, version re-check on reconnect), wired into web.

**DoD:** two browsers — an edit in one appears in the other without user action, verified on prod.

## Decisions (2026-11-22)

- **Raw Spring WebSocket, not STOMP.** One server->client message type (`{"type":"dataVersion","value":N}`); STOMP would be a broker framework to push one integer and would lean the Redis scale path on Spring's relay instead of our own registry. Two-way door, moderate hinge.
- **Handshake auth reuses the API chain.** `/ws` is not public, so the security chain authenticates the upgrade GET (bearer header for mobile, access cookie for web — the cookie rides the handshake same-site, so no token touches JS). `ws/AuthenticatedUserHandshakeInterceptor` copies the authenticated user id onto the session; the handler reads it. Spring's own `setAllowedOrigins` is set to the CORS origins (the handshake is cross-origin web->API) — the cross-site-WebSocket-hijack defence.
- **The registry is local; the broadcaster is the Redis seam.** `ws/WebSocketSessionRegistry` holds this instance's sockets (each wrapped in `ConcurrentWebSocketSessionDecorator` so sends never race), keyed by session id so a close removes the exact one. `ws/DataVersionBroadcaster` is the interface a multi-instance deployment reimplements over Redis pub/sub; `LocalDataVersionBroadcaster` delivers to the registry now. This refines the plan's "registry behind an interface" — the interface sits at the fan-out, which is what actually changes for multi-instance; the socket bookkeeping is local forever.
- **Hello on connect.** The handler sends the account's current `dataVersion` the moment a session opens, so connect and reconnect re-check through the same client path for free — a session that reconnects after missing updates catches up with no extra message.
- **Publish to all + a client monotonic guard, not origin exclusion.** Every committed sync broadcasts to all the user's sessions; the tab that synced receives its own new version and ignores it (not greater than what it already set). "Other sessions" is satisfied behaviourally, with no HTTP<->WS connection correlation. The broadcast runs **after** the commit in `CalendarSyncService` (never inside the transaction, never on the empty-diff or stale paths).
- **Client module host-agnostic** (`client/shared/src/sync/realtimeClient.ts`): the WebSocket itself is injected (a `connect(handlers)` port), so shared never references the browser/native `WebSocket` type. Reconnect with backoff, a debounced behind-check (re-reads the known version at fire time, so the tab's own commit echo and a version the HTTP sync already caught up to are no-ops), and an app-level heartbeat to keep intermediaries warm. `onBehind` = fetch `/calendar/bootstrap` then `adoptFreshServerState` (the exact stale-recovery path).
- **Gated behind `NEXT_PUBLIC_CALENDAR_REALTIME=on`** (`client/web/lib/calendarRealtime.ts`), java-backend-only and impersonation-safe, wired inside `useCalendarServerSync`. Ships dark; flip by env with a redeploy; rollback = unset -> pure HTTP sync, exactly today. Correctness never depends on the socket: a dropped or disabled channel just means a passive tab updates on its next edit instead of instantly.
