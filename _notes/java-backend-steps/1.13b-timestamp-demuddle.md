## Current state (investigated 2026-11-23)

**Shared diff (`client/shared/src/sync/compareCalendarData.ts`).** Engine-output tables (`categoryEvent`, `travelEvent`, `engineMessage`) ALREADY strip `createdAt`/`updatedAt` via `stripDbMetadata` before `objectsAreEqual`. The source tables that still carry the two timestamps INTO the content compare (and into the update payload) are:
- `planner`, `calendar` (SimpleEvent core), `template` — whole-object compare, timestamps included.
- `category` (after `stripTimeSlots`), `queue` (after `stripMembers`), `queueMember` — whole-object compare, timestamps included.
- `dependency` — immutable (create/destroy only), so no content compare; `createdAt`/`updatedAt` appear only in the create payload.

**Java writer (`sync/CalendarChangeWriter.java`).** `createdAt` is client-supplied on create (plain `text` column); `updatedAt` is the server's `now` on every update (`CalendarSyncService` computes `now = ISO_MILLIS.format(clock.instant())`, the `...000Z` 3-digit shape). Engine-output `createdAt` is left to the column default; its `updatedAt` is `now`.

**Columns (all Postgres `TEXT` today).** With a `(now())::text` default: `Categories`, `Queues`, `QueueMembers`, `PlannerDependencies`, `CategoryEvents`, `TravelEvents`. Without a default (client supplies on insert): `Planners`, `SimpleEvents`, `EventTemplates`, and `HabitCompletions` (`createdAt` only — this table has NO `updatedAt`). The Java mirror holds every one of these as `String` under `ddl-auto: validate`.

**Format reason the mirror is `String` (1.3).** The web writes `toISOString()` = `...000Z` (3 fractional digits, UTC) and the diff compares that exact text, so a `String`->`Instant` flip must keep Jackson serializing Instant as `...000Z` or the wire shape and the fixtures drift.

## Decisions (settled 2026-11-23)

1. **Diff-strip breadth: strip everywhere.** Strip `createdAt`/`updatedAt` from ALL source content compares (`planner`/`calendar`/`template`/`category`/`queue`/`queueMember`), mirroring the engine-output tables, so `dataVersion` is the sole OCC token. (`dependency` is create/destroy-only, no change needed.)

2. **`updatedAt` ownership: DB trigger.** A `BEFORE UPDATE` trigger sets `updatedAt = now()` — single source of truth that survives any future writer (incl. mobile), matching the plan's "DB-owned audit" intent. The Java writer STOPS writing `updatedAt` on update (drop the `now` arg on those `updateOwned` calls); the trigger owns it. The trigger is created by the Prisma migration during coexistence and becomes a Flyway object at 2.6.

3. **Physical-migration breadth: all `TEXT` timestamp columns.** Migrate every `createdAt`/`updatedAt` `TEXT` column to `timestamp(3)` for one representation: `Planners`, `SimpleEvents`, `EventTemplates`, `Categories`, `Queues`, `QueueMembers`, `PlannerDependencies`, `CategoryEvents`, `TravelEvents`. The Java mirror flips those fields `String`->`Instant`.

4. **`HabitCompletions`: deferred to 2.1.** Its `createdAt` stays `TEXT` (and `String` in the mirror) for now — it is written by the still-TS `actions/occurrenceCompletions.ts` and never rides the sync diff, so deferring does not weaken the de-muddle. It migrates when its writes move to Java in Phase 2.1 Group A. (This is the one straggler `TEXT` timestamp column after 1.13b; noted so it is not lost.)

5. **`createdAt` stays client-write-once** (immutable recurrence anchor + restore-preserve). The client keeps supplying it on insert as an ISO string cast to `timestamp(3)`; the migration adds no default to the three no-default tables.

## Risks

- **Prod data conversion on live tables.** The migration casts existing `TEXT` ISO strings to `timestamp(3)` (`("col")::timestamptz`-style). Any legacy row whose value is not a clean ISO instant fails the whole migration — audit the existing values first (dev Neon + a prod read) before writing the migration.
- **Serialization drift.** Instant -> JSON must stay `...000Z`; otherwise the regenerated corpus/bootstrap fixtures and the web diff disagree. Verify with a round-trip before regenerating fixtures.
- **Schema authority.** Prisma still owns migrations until 2.6, so the `TEXT`->`timestamp(3)` change (+ any trigger) is a Prisma migration applied in the prod Vercel build (needs `DIRECT_URL`); Java flips `String`->`Instant` and `validate` is the check. Staging branch first, then prod — never two migration systems on one DB.
