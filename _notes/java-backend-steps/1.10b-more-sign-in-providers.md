# 1.10b More sign-in providers: Microsoft + Apple

**Status:** ◐ Code done (2026-11-22), staging rollout pending · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** Sign in with Microsoft and Sign in with Apple next to Google, on the 1.8 machinery (Spring OAuth client, `OAuthAccountService`, the handoff code). Built once for both: an emailed verification step for providers that do not vouch for the email, so such an account is not usable until its owner follows the link.

**DoD:** both providers round-trip on staging from the web login page; a Microsoft sign-in creates no usable account until the emailed link is followed; an email that already has an account is still refused, not linked.

**Ordering:** after 1.10, when the web login page exists. Apple is mandatory once the iOS app offers Google sign-in (App Store guideline 4.8), so this lands before Phase 7 at the latest. The Apple Developer Program membership it needs is enrolled on day 1 of Phase 3 anyway. (Enrolled early, 2026-11-21, so Apple ships with this step.)

## Design decisions (2026-11-21/22)

Docs re-checked at the start (Microsoft Learn ID-token, OIDC and access-token pages; Apple's REST API, client-secret, `id_token` and TN3194 pages); the research notes below held, with the additions here.

- **An email the provider does not vouch for gets a pending sign-up, not a user row.** Table `oauth_pending_signups` (Prisma migration `20261121210000_add_oauth_pending_signups`, appended to the test `schema.sql`): `tokenHash` pk, `provider` + `subject` unique, `email`, `name`, `image`, `createdAt`, `expiresAt`. The emailed link (`/auth/oauth/confirm?token=`, 256 bits, SHA-256 stored, one hour, one per provider account, one-minute resend cooldown) creates the account. Rejected alternative: an unverified user row. It would block the real owner's registration and would need the password reset to strip provider links it never verified.
- **Opening the link creates the account and signs nobody in.** The link proves the address, not the provider login, so the account becomes usable only through a sign-in with that provider account. The web page posts only on a button press: mail scanners open links.
- **The rule is per identity, not per provider.** Every Microsoft email is unvouched; a Google `email_verified: false` and Apple at Work & School (`false`) take the same path. This replaces 1.8's `email_unverified` refusal; a token without any email is now `email_missing`.
- **An address that already has an account is still refused, never linked (DoD).** For a vouched address the browser gets `account_exists` as before. For an unvouched one the browser gets the same `?status=verification_sent` as for a new address and the owner gets the existing-account notice, so nobody can learn which addresses have accounts by naming them at Microsoft.
- **Microsoft accounts key on `oid`, not `sub`.** `sub` is pairwise per app registration, and the registration is shared with calendar import (and was already orphaned once, with the Azure subscription). The `email` claim falls back to `preferred_username` when it looks like an address, which is safe because the address is verified by mail anyway.
- **Microsoft endpoints and issuer.** `common` v2.0 endpoints, no fixed issuer URI; `MicrosoftIssuerValidator` requires `tid` to be a GUID and `iss` to equal `https://login.microsoftonline.com/{tid}/v2.0`. Not checked: the issuer restriction on each signing key, because the ID token comes straight from the token endpoint over TLS in exchange for our own code and secret. `prompt=select_account`, since people hold both personal and work accounts.
- **Apple specifics.** ES256 client secret signed per token request (5-minute lifetime, `AppleClientSecret`); `response_mode=form_post`; PKCE switched off (Spring 7 turns it on by default; Apple documents no PKCE parameters, and the nonce binds the code to the session); name from the first callback's `user` form field, sanitized. The POST callback needed two changes: the `circadium_oauth` cookie is `SameSite=None` outside `local` (browsers never send Lax cookies on cross-site POSTs), and `CorsConfig` leaves `/login/oauth2/code/**` alone (the POST carries Apple's `Origin`).
- **Apple's refresh token is stored; this reverses 1.8's "never store provider tokens" for Apple only.** TN3194: `/auth/revoke` is the only way to end the app's authorization, and App Store review requires account deletion (5.1.1(v)). It sits in `accounts.refresh_token`, refreshed on every Apple sign-in, and `AccountDeletionService` revokes it after the commit (`AppleRevocationClient`: background, 3 retries, Sentry on failure). Plain text, because it is useless without the client secret, which only the server's key can sign.
- **`OAUTH_PROVIDERS` (server) and `NEXT_PUBLIC_OAUTH_PROVIDERS` (web)** list the providers offered (default all three). Outside `local`, every listed provider must be configured or startup fails. Narrowing both is how a provider is rolled out on purpose.
- **Microsoft credentials reuse `MICROSOFT_CLIENT_ID` / `MICROSOFT_CLIENT_SECRET`**, the calendar-import registration's names, so 2.3 finds them already set on Fly.
- **Separate Apple Services IDs per environment** (`app.circadium.web`, `app.circadium.web.staging`). Apple's `sub` is per team, so with one shared Services ID a staging account deletion would revoke the same person's prod authorization.

### API (new or changed)

| Endpoint | Input | Responses |
|---|---|---|
| `GET /oauth2/authorization/{google,microsoft,apple}` | `client`, `challenge` | 302 to the provider; 400 / 404 / 405 as in 1.8 |
| `GET` (Apple: `POST`) `/login/oauth2/code/{provider}` | `code`, `state` (Apple also `user`) | 302 to the completion URL with `?code=`, `?status=verification_sent`, or `?error=` `access_denied` / `account_exists` / `email_missing` / `oauth_failed` |
| `POST /auth/oauth/confirm` | `token` (43 chars) | 200 `{"provider":"microsoft"}`, no cookies; 400 `invalid_token` / `expired_token`; 409 `email_in_use` |

New audit events: `OAUTH_SIGNUP_PENDING` (detail the provider, `+ resend_cooldown` when no mail went out), `OAUTH_SIGNUP_LINK_FAILURE` (`unknown_link` / `expired_link` / `email_in_use`); `OAUTH_REGISTER` from a link has detail `microsoft email_link`. Rate limits: the start and callback rules are per path pattern now (one OAuth bucket for all providers, Apple's POST callback included); `POST /auth/oauth/confirm` is on the account-link bucket (10/min/IP).

## Rollout

Staging first; prod at the merge to `main`. A push to `feature/server` deploys staging, so the switches go in before the push.

1. **Hold the new providers back:** `OAUTH_PROVIDERS = "google"` sits in the `[env]` of both `fly.toml` and `fly.prod.toml`, so the push (and later the merge) carries the switch itself. The web side needs `NEXT_PUBLIC_OAUTH_PROVIDERS=google` on the staging Vercel project (Production environment) before the push, or the login page shows Microsoft and Apple buttons the API refuses. Then push; the Vercel build applies the migration. Each later step widens both lists (edit the toml, update the Vercel value, push).
2. **Microsoft staging app** ("Circadium Staging", decided 2026-11-21): Entra admin center → App registrations → New, "Accounts in any organizational directory and personal Microsoft accounts". Web redirect URIs `https://api.staging.circadium.app/login/oauth2/code/microsoft`, `https://staging.circadium.app/api/integrations/microsoft/callback`, `http://localhost:8080/login/oauth2/code/microsoft`. API permissions (delegated): `openid`, `email`, `profile`, `offline_access`, `Calendars.Read`. The user enters the values:
   - **Client ID:** Overview → "Application (client) ID" (not the Object ID or the Directory (tenant) ID).
   - **Client secret:** Certificates & secrets → Client secrets → New client secret (180 days up to the 24-month maximum). Copy the **Value** column at once; it is shown only once, and the "Secret ID" GUID next to it is not the secret (using it fails with `invalid_client`).
   - **Both places, same values** (Java uses the registration for sign-in, the web for calendar import): `fly secrets set MICROSOFT_CLIENT_ID=... MICROSOFT_CLIENT_SECRET=... --stage -a circadium-server-staging` (or the Fly dashboard, to keep the secret out of shell history); from `client/web`, `vercel env add MICROSOFT_CLIENT_ID production` and `vercel env add MICROSOFT_CLIENT_SECRET production` (the staging project's Production environment serves staging.circadium.app). Both apply from the next deploy.
   - **Turn it on:** `OAUTH_PROVIDERS = "google,microsoft"` in `fly.toml`, and `NEXT_PUBLIC_OAUTH_PROVIDERS=google,microsoft` on the staging Vercel project (`vercel env update NEXT_PUBLIC_OAUTH_PROVIDERS --environment production --yes`, value on stdin; it changes the value in place, where `rm` + `add` would need a human to approve the removal; the value is baked in at build time). Done for staging 2026-11-22. One push deploys both. Server first would be harmless, but web first would show a button the API answers with `unknown_provider`. A missing secret fails the new release's health check, and the old release keeps serving.
   - **Expiry:** recorded in the Expires column. Afterwards staging's Microsoft sign-in and calendar import fail with `AADSTS7000222`. Set a reminder two weeks ahead. To rotate with no downtime: add a second secret, update Fly and Vercel, deploy, then delete the old secret. The prod registration's secret works the same way; check its date before the merge.
3. **Apple** once the membership is active: App ID with Sign in with Apple; Services IDs `app.circadium.web.staging` (domain `api.staging.circadium.app`, return URL `https://api.staging.circadium.app/login/oauth2/code/apple`) and `app.circadium.web` (`api.circadium.app`); one Sign in with Apple key (`.p8`, downloadable once); email source `circadium.app` under Sign in with Apple for Email Communication. Then add `apple` to both lists (or unset both, which means all three).
4. **DoD on staging:** a new Microsoft sign-in lands on "check your email", creates no `users` row, and the link's button creates the account, after which Microsoft sign-in works; a Microsoft sign-in with an existing account's address leaves no `accounts` row and mails the owner a notice; Apple round-trips from the login page (name captured on first sign-in, refresh token on the `accounts` row); deleting a test Apple account removes Circadium from the Apple ID's "Sign in with Apple" list.
5. **Prod at the merge:** prod Vercel `NEXT_PUBLIC_OAUTH_PROVIDERS=google` before the merge (matching `fly.prod.toml`). To widen: the prod Microsoft registration (found 2026-11-21) gets `https://api.circadium.app/login/oauth2/code/microsoft`, and its secret expiry is checked; Fly prod `MICROSOFT_*` and `APPLE_*` (Services ID `app.circadium.web`); then both prod lists.

## Follow-ups

- **Apple server-to-server notifications** (`consent-revoked`, `account-delete`, `email-disabled`): TN3194 expects a web service to react to `consent-revoked` by dropping the stored token and signing the user out. Needs an endpoint registered on the Services ID that verifies Apple's signed payload. Not built; before Phase 7.
- **Native Sign in with Apple on iOS (Phase 3)** issues ID tokens whose `aud` is the app's bundle ID, not the Services ID. The server then needs a token-exchange path that accepts that audience; the web flow here does not cover it.
- **Linking another provider to an existing account** (settings, authenticated): still not built; the settings card says so.
- **Microsoft publisher verification**, for work tenants that block user consent to unverified multi-tenant apps (research notes above).
- **Existing-account notices from Microsoft sign-ins** are bounded only by the 20/min/IP callback bucket and Microsoft's own login. Add a per-address cooldown if one is ever abused.
- **Privacy page:** does not list Fly.io, which hosts the API and so processes every request. Noticed while editing the provider list; not changed here.

## Research notes (2026-11-20, from the providers' docs; re-check when starting)

**Why the verification step.** 1.8 creates an account only when the provider vouches for the email (Google's `email_verified`). Without that, someone could create a Circadium account under another person's address through the provider; when the real owner later resets the password through the emailed link and gets in, the other person's provider login is still attached. The 1.7 verification-mail plumbing (`AccountTokens`, `AccountMailer`) is the starting point.

**Microsoft**
- The `email` claim "isn't guaranteed to be correct and is mutable over time. Never use it for authorization." Microsoft says not to identify users by human-readable data: use `sub` (pairwise per app) or `oid` (per tenant) with `tid`. There is an optional `xms_edov` claim ("email domain owner has been verified"), but its enablement is not documented in the optional-claims reference, and the docs do not say personal-account emails are verified. Plan: treat every Microsoft email as unverified and send our own verification.
- Account matching stays `(provider, subject)`; there are no NextAuth-era Microsoft rows, so `sub` is free to choose.
- Spring has no Microsoft preset; endpoints are configured by hand. With the multi-tenant (`common`) endpoint the ID token's `iss` contains the user's tenant id, so Spring's fixed-issuer check needs a custom validator (accept the issuer pattern, check it matches `tid`).
- Portal: the Entra app registration used for calendar import (`MICROSOFT_CLIENT_ID`) can be reused or a separate one made; add the redirect URIs.
  - The prod registration still exists (found 2026-11-21). The Azure subscription was deleted after the free credit ran out on 2026-10-01, but app registrations live in the directory, which survived.
  - Staging has no Microsoft app at all (no `MICROSOFT_*` on the `circadium-staging` Vercel project), so Microsoft calendar connect has never worked there. Decided 2026-11-21: create a separate "Circadium Staging" registration here, as staging already has its own Google client and Resend key. It needs personal and work accounts, delegated `Calendars.Read` + `offline_access`, the redirect URIs `https://staging.circadium.app/api/integrations/microsoft/callback` plus this step's Java callback on `api.staging.circadium.app`, and `MICROSOFT_CLIENT_ID` / `_SECRET` on the staging Vercel project (the user enters the values).
  - Client secrets expire (the portal suggests 6 months). Check the prod secret's expiry when starting. Personal accounts (consumer tenant `9188040d-6c67-4c5b-b112-36a304b66dad`) work without more. Some work/school tenants (risk-based step-up consent on) block user consent to unverified multi-tenant apps registered after November 2020; publisher verification is free but needs a Microsoft AI Cloud Partner Program account, an app registered with a work account, and a custom publisher domain (not `*.onmicrosoft.com`).

**Apple** (from general knowledge, verify against Apple's docs when starting)
- OpenID Connect, with verified emails, including "Hide My Email" private-relay addresses.
- The client secret is a JWT signed with an Apple private key (ES256) that expires at most every 6 months, so it must be generated by the server rather than stored as a static secret.
- When name or email is requested, Apple returns to the callback with an HTTP POST (`response_mode=form_post`); the OAuth chain and the rate limiter must accept POST on the Apple callback.
- The user's name arrives only on the first authorization; capture it then.
- Mail to private-relay addresses only gets through if the sending domain is registered with Apple; register the Resend sending domain, or verification and notice mails bounce.

**Shared changes**
- `OAuthLoginHandler` assumes Google's OIDC user; map each provider's identity explicitly.
- Rate-limit entries are per provider path; switch to the OAuth path prefixes.
- Tests: generalize `FakeGoogle` into a fake provider.
- Web login buttons, the settings providers card, the privacy policy's provider list.

**Meta / Facebook: evaluated and skipped.** Facebook Login on the web is OAuth 2.0 plus a Graph API `/me` call (no OpenID Connect), with no verified-email indicator and no guarantee an email is returned. `email` and `public_profile` need no App Review, but going Live needs a data-deletion callback (a signed POST answered with a status URL and confirmation code) or a deletion-instructions page, and Advanced Access needs Business Verification. Too much for too little in a productivity app.
