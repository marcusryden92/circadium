## Timestamp decision point (SimpleEvent.start/end TEXT vs timestamp(3))

The scan `WHERE "start" >= $from AND "start" < $to` is the first server-side time-range query.

- **Measured reality:** prod volume is ~180 SimpleEvents for the one real account, single-digit
  users total. Either representation answers in microseconds; performance does NOT decide this.
  What decides it is correctness-by-construction: lexicographic TEXT compare is only sound
  while every row shares the exact `.SSS'Z'` shape, which holds today only because the web's
  `toISOString()` is the sole writer.
- **Lean: migrate `SimpleEvents.start/end` → `timestamp(3)` in this step.** The whole seam
  already exists from 1.13b/2.1/2.2/2.4: hand-written Prisma migration (`USING ... ::timestamp`),
  entity `String` → `Instant`, the sync writer's `Column.timestamp()` (ISO text in,
  `::timestamp(3)` cast — BulkStatements:70), wire stays `.SSSZ` ISO via the Jackson Instant
  shape, web re-types in `types/prisma.ts` (`WithIsoTimestamps` pattern), conformance asserts
  catch stragglers. Add the index the scan wants (`(start)` or `("userId", start)`) in the same
  migration.
- **Planner datetimes riding along** (`deadline`, `starts`, `earliestStartDate`,
  `completedStartTime`, `completedEndTime`) + `HabitCompletions.start/end`: the master says they
  ride the same call, BUT audit actual value shapes on prod first — SimpleEvent start/end are
  engine-written `toISOString()` (uniform, verified in the 2.4 export), while the Planner
  columns are form-written and may hold mixed shapes (a non-ISO or local-naive string would
  change meaning under `::timestamp`). If the audit finds anything but clean `Z`-suffixed ISO,
  migrate SimpleEvents alone here and leave the Planner half for its own pass. The audit is one
  SQL regex pass per column; do it at implementation start.

## Recon (2026-11-25)

### What exists server-side

- **Jobs pattern:** `jobs/SchedulingConfig` (ShedLock on the Postgres `shedlock` table,
  `usingDbTime`, default lock PT30M) + `jobs/TravelTopUpJob` (`@Scheduled` cron +
  `@SchedulerLock`, JdbcTemplate scan over users, one account's failure never starves the rest,
  quiet logging). The push scheduler is the second job in this mold — but minute-cadence
  (`fixedDelay` or `cron */5`), not nightly, so `lockAtMostFor` must stay under the cadence
  and the scan must be cheap.
- **External-client pattern:** `external/maps` (`PlacesClient`/`RoutesClient` interfaces, REST
  impls over `RestClient`, retry on 429/5xx, fakes in `TestcontainersConfiguration`). The Expo
  client follows it: `external/push/ExpoPushClient` interface + REST impl + recording fake. No
  third-party Expo SDK — the API is two JSON POSTs.
- **Auth:** `POST /devices/register` is an authenticated API-chain endpoint (NOT in
  PUBLIC_ENDPOINTS); mobile sends `Authorization: Bearer` (ClientType mobile), which already
  works. Nothing new in SecurityConfig beyond the route being non-public by default.
- **Java-only tables precedent:** `sessions`, `audit_log`, `shedlock`, `oauth_handoff_codes`
  are hand-written SQL in Prisma migrations with NO Prisma models (the web never reads them);
  Java validates under `ddl-auto: validate`. `device_push_tokens` + `sent_notifications` do the
  same. Snake_case names + snake_case columns (Java-era convention, vs the Prisma-era
  camelCase-quoted tables).

### Engine-output rows (the scan source)

- `SimpleEvents`: `start`/`end` TEXT (uniform `.SSS'Z'` ISO, engine-written), only index is
  `("userId")`. `EventExtendedProps` (1:1 on `eventId`) carries `eventType`
  (`planner|template|travel|category|external`) and `completedStartTime/End`. The scan wants:
  events with `eventType = 'planner'`, start inside `[now+lead, now+lead+window)`, uncompleted,
  joined to the user's registered devices, anti-joined to `sent_notifications`.
- Event ids are engine-deterministic (planner id, `${plannerId}|chunk:n`,
  `${planId}|${localStartKey}`, …) and a regen rewrites rows wholesale but `stabilizeEvent`
  keeps ids stable for unmoved events. A MOVED event keeps its id with a new `start` — so the
  dedup key must include the start instant: a rescheduled event legitimately re-notifies at its
  new time, and the stale row for the old time simply never matches a future scan.
- Title for the notification body comes off the row (`title`); deep-link route can ride the
  push `data` (`/calendar` v1, per the capacitor-plan tap-routing precedent).

### Expo Push API (verified against current docs)

- Send: `POST https://exp.host/--/api/v2/push/send`, JSON array ≤100 messages
  (`{to: "ExponentPushToken[...]", title, body, data, channelId}`), gzip accepted. Response:
  one **ticket** per message — `{status:"ok", id}` or `{status:"error", details:{error:
  "DeviceNotRegistered"|...}}`. A ticket error `DeviceNotRegistered` → prune the token NOW.
- Receipts: `POST https://exp.host/--/api/v2/push/getReceipts` with ticket ids, available
  ~15 min after send, retained ~24h. Receipt `DeviceNotRegistered` → prune;
  `MessageRateExceeded` → back off and retry later. Not every ticket has an id (enqueue
  failures carry error info instead) — handle both.
- Tickets→tokens must be mapped BY US (receipts are keyed by ticket id only): store the ticket
  id on the `sent_notifications` row.
- Optional account-level push security (Bearer access token) exists; off by default — add the
  env hook (`EXPO_PUSH_ACCESS_TOKEN`, optional in every profile) but don't require it.
- Android delivery needs the app built with FCM v1 credentials (EAS-managed); iOS needs APNs
  (blocked on Apple membership — Android-only DoD for now).

### Table + flow sketch

- `device_push_tokens`: `id` uuid pk, `user_id` FK→users cascade, `token` UNIQUE
  (`ExponentPushToken[...]`), `platform` text, `device_name` text null, `created_at` /
  `last_seen_at` timestamp(3). Register endpoint upserts by token — re-registration from a
  different signed-in account re-owns the token (one physical device, latest account wins);
  repeat registration bumps `last_seen_at`. Prune = delete row.
- `sent_notifications`: `id` uuid pk, `token_id` FK→device_push_tokens cascade, `event_id`
  text, `event_start` timestamp(3) (or text if the migration is deferred), `sent_at`
  timestamp(3), `ticket_id` text null, `receipt_checked_at` timestamp(3) null,
  UNIQUE (`token_id`, `event_id`, `event_start`). **Dedup by design:** the scheduler CLAIMS
  first — `INSERT ... ON CONFLICT DO NOTHING RETURNING id` — and only sends what it claimed, so
  two instances (or a crash-retry) can never double-send; ShedLock is belt on top of that
  braces.
- `PushScheduler` job (every 5 min, ShedLock'd): claim-scan → batch ≤100 to ExpoPushClient →
  write ticket ids / prune ticket-level dead tokens. A second pass in the same job (or a
  companion `@Scheduled`) fetches receipts for rows `sent_at < now-15min AND
  receipt_checked_at IS NULL`, prunes `DeviceNotRegistered` tokens, stamps
  `receipt_checked_at`. A retention sweep deletes `sent_notifications` older than ~7 days
  (nightly, can ride the same job class).
- `POST /devices/register` body `{token, platform, deviceName?}` → 204; validate the
  `ExponentPushToken[` shape. A `DELETE /devices/{token}` (sign-out path) is cheap and lets the
  mobile app unregister on logout — include it.
- Integration tests: fake ExpoPushClient recording sends; pin claim-before-send (concurrent
  double-run sends once), moved-event re-notify, completed/non-planner exclusion, ticket-level
  and receipt-level pruning, cross-user isolation. No test reaches the network (maps/mail
  precedent).
