## Design decisions (2026-11-22)

- **Shape:** `BootstrapPayload` from `client/shared/src/contracts/wire.ts`, which is what `fetchFreshState` (the stale-sync path) already returns: `fetchCalendarData`'s data plus `locations` and `travelTimes` (the web loads those two separately today, through `fetchAllSchedulingData`). The bare payload, no `{success, data}` wrapper; errors are ProblemDetail. Records in `calendar/CalendarContracts.java`, one per contract type, named as in the TS.
- **`categories[].location` dropped everywhere.** Both TS fetchers joined the full Location row into every category, but the contract's `Category` has no `location` and nothing on the client reads it (checked every `.location.` access in `client/web` and `client/shared`). Removed from `fetchCalendarData` and `fetchFreshState` too, so all three agree with the contract.
- **"Byte-for-byte" means equal JSON values.** Java writes `0.0` where JavaScript writes `0`, and key order differs; `JSON.parse` gives the client the same thing. Lists are ordered by id (Prisma's order is undefined, so nothing on the client can depend on it); locations oldest first (`createdAt`, then id), as the web orders them.
- **One snapshot.** All queries run in one read-only `REPEATABLE READ` transaction, so `dataVersion` describes exactly the rows returned. The TS runs ~12 separate queries; it reads `dataVersion` first, so its worst case is a needless stale round trip, while the reverse order would let a client sync on rows it never saw.
- **Isolation is set by `SET TRANSACTION ISOLATION LEVEL REPEATABLE READ` as the transaction's first statement, not `@Transactional(isolation = ...)`.** PgJDBC applies the latter with `SET SESSION CHARACTERISTICS`, sent outside the transaction, and both environments connect through Neon's pooled host (PgBouncer, transaction pooling), which can run that statement on a different server connection than the transaction, and leaves it set there for other clients. Read-only is safe: PgJDBC's default `readOnlyMode=transaction` sends `BEGIN READ ONLY`. Rule added to `server/CLAUDE.md`.
- **Child rows are selected through their parent**, as Prisma's `include` does: time windows through the user's categories, queue members through the user's queues, `extendedProps` through the user's events. A window whose category was deleted (`categoryId` null) is left out.
- **`engineMessages[].payload`** is the stored jsonb text passed through (`@JsonRawValue`). Postgres normalizes jsonb (key order, spacing), so it is not the text the client wrote, but it is the same value Prisma parses.
- **A missing user row** (deleted between the token check and the query) answers 401 `account_not_found`, like the `/account` endpoints. `Cache-Control: no-store`.
- **springdoc:** `springdoc.default-produces-media-type: application/json`, otherwise every response body is listed as `*/*`.

## Golden fixture

- `server/src/test/resources/calendar/bootstrap-seed.sql` (two accounts; nulls beside values, a fractional `sortOrder`, an event without `extendedProps` and one with a null `plannerType`, Sunday and Saturday, object/string/array payloads, an unroutable travel time, an orphan time window) and `bootstrap-expected.json`.
- The expected JSON is the web's own `fetchFreshState` output for the seed, written by `client/web/__tests__/contracts/captureBootstrapFixture.test.ts`: `pnpm fixture:bootstrap` from `client/web` with the dev database container up. It builds a scratch database `circadium_bootstrap_fixture` in that container from the server's test `schema.sql` plus the seed, runs `fetchFreshState`, writes the JSON sorted by id, and drops the database. A Jest file because Jest is what resolves the web's `@/` imports; skipped unless `CAPTURE_BOOTSTRAP_FIXTURE` is set.
- `CalendarBootstrapIntegrationTest` (5): the golden comparison (JSONAssert `NON_EXTENSIBLE`: no missing or extra keys, numbers by value, arrays in any order) plus the locations order; a new account gets every list empty and version 0; no token 401; an unknown user 401 `account_not_found`; the OpenAPI document references `BootstrapPayload`. Checked that the comparison fails on a changed value and on an extra key.
- Recapture whenever the seed or the TS fetcher changes, and after 1.12's timestamp de-muddle.

## Follow-ups

- **1.12 cannot call `CalendarBootstrapService.load` inside the sync's transaction.** `load` joins an existing transaction, and `SET TRANSACTION` fails once that transaction has run a query. The stale response needs its own transaction after the failed version check rolls back (or a variant without the `SET`).
- **The OpenAPI schema does not mark fields required or nullable.** The production baseline's OpenAPI-vs-contracts drift check has no step yet and will need those markers.
- **Response compression:** a calendar with thousands of events makes a large body. Consider `server.compression` before 1.13 makes the web depend on this endpoint.
