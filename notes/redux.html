How Redux actually works here

This store does not look like a textbook Redux app. Components almost never dispatch a reducer directly — they call a hook that dispatches one thunk, and that thunk orchestrates pruning, an optimistic write, a Web-Worker engine run, and the derived write-back. The trick to reading all of it is one split: state you author vs state the engine derives.

2 · The write path — one edit through the thunk

The flow goes down the middle: a component calls the hook, the hook dispatches the thunk, the thunk writes source optimistically and then writes engine output after the worker replies. Components read back via useSelector (the dashed arrows arcing up the sides). That round trip is the Redux cycle.

3 · Each core slice has exactly three write paths

Once you know these three, every dispatch in the codebase is one of them. Nothing else writes calendarSource or engineOutput.

hydrate*

hydrateSource · hydrateEngineOutput

Wholesale replace from a server snapshot. Called on initial load, stale-adoption, and rollback. Clears the undo stacks — the local lineage diverged.

set* (edit)

setPlannerAndTemplate · setCategories · setQueues · setDependencies

The optimistic edit. Dispatched by the thunk before the await, so the UI updates instantly and rapid prev => next calls chain off fresh state.

applyEngineRun

applyEngineRun

The derived write-back. Dispatched by the thunk after the worker returns, in the same tick the edited source settled. One engine run, one dispatch.

Undo / redo live inside calendarSource as past / future stacks of array references (O(1), because every update is immutable). The reducers only move the stacks; the actual restore replays a snapshot back through the same thunk — so pruning, the regen, and the diff sync all still happen.

4 · The whole store — 9 slices, 4 groups

One line governs the model: does the slice ride the OCC diff sync? The first two do. Settings + user feed the engine. The out-of-band three mirror wholesale and never bump dataVersion. Two are pure UI.

Synced core — the two lifecycles above

calendarSource
User-authored inputs + undo stacks.
engineOutput
Engine-derived, ephemeral scores.

Synced support — feed the engine

schedulingSettings
Buffer, transport mode, travel rows (sole source of truth), locations, strategy weights. The engine's travel matrix is derived from this each run.
user
Current user profile + flags (e.g. the userId that stamps generated events).

Out-of-band — direct actions, mirrored wholesale, never bumps dataVersion

externalCalendar
ICS / Google / Microsoft sources + events. Engine reads via deriveExternalBusyEvents.
occurrenceCompletions
Completion log rows. Engine reads via deriveOccurrenceCompletions.
habits
Buckets + trackers + links. The engine never reads it.

UI-only — pure client state

toasts
Transient toast queue (incl. Undid / Redid).
syncStatus
Drives the save indicator for the sync loop.
