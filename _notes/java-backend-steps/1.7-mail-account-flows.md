### API

| Endpoint | Auth | Body | Responses |
|---|---|---|---|
| `POST /auth/verify-email` | public | `token` | 200 `{status: EMAIL_VERIFIED}`; 400 `invalid_token` / `expired_token`; 409 `email_in_use` |
| `POST /auth/password-reset` | public | `email` | 202 `{status: RESET_EMAIL_SENT}` always |
| `POST /auth/password-reset/confirm` | public | `token`, `password` (8+ chars, ≤72 bytes) | 200 `{status: PASSWORD_UPDATED}`; 400 `invalid_token` / `expired_token` / validation |
| `POST /account/deletion` | bearer | `confirmEmail`, `password` (required if the account has one) | 202 `{status: CONFIRMATION_EMAIL_SENT}`; 400 `email_mismatch` / `password_required`; 403 `bad_password`; 429 |
| `POST /account/deletion/confirm` | bearer | `token` | 200 `{status: ACCOUNT_DELETED}`; 400 `invalid_token` / `expired_token`; 403 `wrong_account` |

Errors are ProblemDetails with a stable `code` property. All responses carry `Cache-Control: no-store`. Rate limits per IP: password-reset 5/h, the other four 10/min.

### What was built

- **`external/mail/`**: `ResendAccountMailer` (RestClient → `POST https://api.resend.com/emails`, background pool of 2–4 threads with a 500-message queue, up to 3 attempts on 429/5xx/network errors with one `Idempotency-Key`, no retry on other 4xx, final failure logged and sent to Sentry). `AccountEmails` ports the branded HTML layout from `lib/mail.ts` and adds plain-text parts. `MailConfig` picks Resend or the logging fallback. `MailProperties` (`circadium.mail`).
- **`auth/EmailVerificationService`**: ports `newVerificationAction.ts`, including email-change tokens (`userId` set → move the account to the token's address; 409 if another account took it).
- **`auth/PasswordResetService`**: ports `reset.ts` + `newPassword.ts`. OAuth-only accounts get no mail. Confirming sets the hash and `passwordChangedAt` (which also ends NextAuth sessions), revokes every Java refresh session, lifts the lockout, and emails a "password changed" notice.
- **`auth/AccountDeletionService`**: ports `deleteAccount.ts`. The request re-checks the password (a wrong password feeds the login lockout) and mails a 30-minute link. The confirm only works for the account that requested it. The delete removes `UserSchedulingPreferences`, the email-keyed token rows and the lockout row explicitly; everything else goes through the `users` FK cascades.
- **`auth/AccountTokens`**: password-reset tokens (1 h, one per email, 1-minute resend cooldown derived from `expires`) and deletion tokens (30 min, one per user). Every consume is a `delete ... where token = ?` that must return 1, so a link works exactly once even under concurrent clicks.
- **Registration**: a duplicate now emails the owner an "already have an account" notice (OAuth-only owners are pointed at Google/GitHub), and the duplicate path does one bcrypt hash so its timing matches a real registration.
- **Audit events**: EMAIL_VERIFIED, EMAIL_CHANGED, PASSWORD_RESET_REQUESTED (detail `unknown_account` / `cooldown`), PASSWORD_RESET, ACCOUNT_DELETION_REQUESTED, ACCOUNT_DELETION_DENIED (`bad_password` / `locked` / `wrong_account`), ACCOUNT_DELETED.
- `auth/PasswordPolicy` (72-byte bcrypt ceiling, shared by register and reset), `auth/AccountFlowException`.

### Design decisions

- **Mail is asynchronous.** Requests never wait on Resend, so "account exists" and "account doesn't" paths cost the same time, and a Resend outage doesn't turn registration into 500s. The cost: deletion no longer reports a failed send (the web did); the user just requests again.
- **Audit and mail happen after commit.** `audit_log` cascades from `users` and `AuditLogger` writes in a separate transaction, so an audit row for a user the current transaction has locked (email change takes a `FOR UPDATE` lock because `email` is unique; deletion obviously does) would block forever. Each flow does its writes in a `TransactionTemplate` block and audits afterwards.
- **ACCOUNT_DELETED keeps no personal data**: `userId` and `email` are null (the row would otherwise cascade away with the user); `detail` holds the opaque former id, and the IP is kept as the security record.
- **Startup fails without a Resend key outside `local`** (same pattern as signing keys), so a misconfigured deploy can't silently drop verification and reset mail.
- **Links open the existing web pages** (`/auth/new-verification`, `/auth/new-password`, `/auth/confirm-deletion`). Those pages still consume tokens through the web's server actions against the same tables, so links mailed by Java work today; the Java endpoints are what the web calls after the auth flip (1.10) and what mobile will call.

## Staging DoD checklist

1. ~~Fly secrets~~ done (above).
2. Registration: register a real mailbox → open the mail → `POST /auth/verify-email` with the token from the link → login returns AUTHENTICATED.
3. Password reset: `POST /auth/password-reset` → mail arrives → `POST /auth/password-reset/confirm` → "password changed" mail arrives → old password 401, new password logs in, old refresh token 401.
4. Account deletion: log in → `POST /account/deletion` with the access token → mail arrives → `POST /account/deletion/confirm` → user row gone, `audit_log` has ACCOUNT_DELETED.
5. Duplicate registration of the same mailbox → "already have an account" mail.

## Follow-ups

- **PostHog erasure on deletion.** The web action deletes the PostHog person after the account; Java does not (no PostHog key server-side yet). Add it when the web flips to the Java endpoint (1.10) or with the rest of account deletion in 2.4.
- **Access tokens outlive a reset or deletion by up to 15 minutes.** Refresh sessions are revoked immediately; checking `passwordChangedAt` / user existence on every request would cost a DB read per call. Endpoints added later must treat a missing user as 401.
- **Email-change flow.** The verify endpoint consumes email-change tokens, but issuing them (settings → change email) is still the web's server action; port it with settings (Phase 2), including a notice to the *old* address (ASVS 2.2.3).
- **Hash the token columns** (store SHA-256 like refresh tokens) once the web stops reading these tables (after 2.6).
- The existing-account notice has no per-address cooldown (the per-IP register limit of 5/h is the only bound); add one if it gets abused.
- Mail queue is in memory: messages queued at shutdown get up to 10 s to send. Fly's default kill timeout is 5 s; raise `kill_timeout` if mail loss on deploy shows up.
