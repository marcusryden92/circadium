# 1.8 OAuth

**Status:** ☑ Done (2026-11-20) · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** Google authorization-code with PKCE, `state`, exact redirect URIs; `Account`-table linking (existing rows keep working); both web and mobile complete through a one-time 60s handoff code → `POST /auth/handoff`. Security checklist reviewed item-by-item (state entropy, code single-use, no token leakage in logs/referrers).

**DoD:** Google round-trips on staging; an existing OAuth user's account links, not duplicates.

**Decision (2026-11-19): GitHub login is dropped.** Unused (no users have signed up with it), so Java implements Google only. Removed from the web (NextAuth provider, login button, settings providers row, privacy page, env docs) and from the server's existing-account email wording.

## Design decisions (2026-11-20)

- **Spring Security `oauth2-client` runs the exchange with Google** (answers the 2026-11-15 reviewer note): state, PKCE, OIDC nonce, ID-token verification against Google's keys, the token request. We own what happens after: account matching, the handoff code, the redirects. The cost is a short server-side session for the round trip (below).
- **Web completes like mobile, through the handoff code** (the original task said "web completion sets cookies"). Setting cookies is 1.9's job, and on staging the API (`fly.dev`) and the web (`vercel.app`) are different sites, so a cookie the API set during the Google redirect would not be usable by the web anyway. With the handoff, OAuth ends in the same token response as `/auth/login`; whatever 1.9 does for login cookies covers OAuth too.
- **An email that already has an account is refused, not linked** (NextAuth's `OAuthAccountNotLinked` parity). Auto-linking by email allows pre-account takeover: someone registers the address with a password first, Google later vouches for it, and their password keeps working on the owner's account.
- **Google's tokens are never stored.** NextAuth stored access/id tokens on `accounts`; Java writes identity only (and a no-op `OAuth2AuthorizedClientRepository` stops Spring keeping them in memory). Calendar access already has its own grant.
- **The emailed 2FA step does not apply to Google sign-in** (NextAuth parity: its `signIn` callback only checked 2FA for credentials). Google authenticated the user.

**111 tests green** (`.\mvnw.cmd verify`), 13 new in `OAuthLoginIntegrationTest`, driven against `FakeGoogle` (a local HTTP server standing in for Google's token and key-set endpoints, issuing really signed RS256 ID tokens that Spring verifies). ### Flow

```
client -> GET /oauth2/authorization/google?client=web|mobile&challenge=<S256(verifier)>
          OAuthStartFilter validates, starts a fresh session holding client + challenge
          Spring redirects to Google with state, PKCE S256 challenge, nonce, exact redirect_uri
Google -> GET /login/oauth2/code/google?code&state
          Spring checks state, exchanges the code (+PKCE verifier, +secret), verifies the ID token
          OAuthLoginHandler: OAuthAccountService matches/creates the account, ends the session,
          redirects to the client's completion URL with ?code=<handoff> or ?error=<reason>
client -> POST /auth/handoff {code, verifier}   -> same token JSON as /auth/login
```

### API

| Endpoint | Auth | Input | Responses |
|---|---|---|---|
| `GET /oauth2/authorization/google` | public (browser navigation) | `client` = `web`/`mobile`, `challenge` = base64url SHA-256 of the client's verifier (43 chars) | 302 to Google; 400 `invalid_request`; 404 `unknown_provider`; 405 for non-GET |
| `GET /login/oauth2/code/google` | public (Google's redirect) | `code`, `state` (or `error`) | 302 to the completion URL with `?code=` or `?error=` `access_denied` / `account_exists` / `email_unverified` / `oauth_failed` |
| `POST /auth/handoff` | public | `code` (43 chars), `verifier` (RFC 7636: 43-128 unreserved chars) | 200 token JSON (`no-store`); 400 `invalid_code` (unknown, used, expired or wrong verifier all look the same) |

Completion URLs (config, never from the request): web `${WEB_BASE_URL}/auth/oauth/complete`, mobile `circadium://auth/oauth/complete`.

### What was built

- **`auth/oauth/`**: `OAuthClientConfig` (Google registration from Spring's preset + `requireProofKey`, scopes `openid email profile`, redirect URI `${AUTH_ISSUER}/login/oauth2/code/google`; outside `local` startup fails without `GOOGLE_CLIENT_ID`/`GOOGLE_CLIENT_SECRET`, `local` without them disables Google sign-in), `OAuthProperties` (`circadium.oauth`), `OAuthClient` (web/mobile), `OAuthStartFilter`, `PendingOAuthLogin` (the session attribute), `OAuthLoginHandler` (success + failure), `OAuthAccountService`, `OAuthHandoffCodes`, `OAuthHandoffController`.
- **`config/SecurityConfig`**: a second filter chain, ordered first, matching only `/oauth2/authorization/**` and `/login/oauth2/code/**`; the only place a session may be created. The API chain gains `POST /auth/handoff` as public.
- **Session cookie** `circadium_oauth`: HttpOnly, Secure (not under `local`), SameSite=Lax (Google's redirect back is a cross-site navigation; Strict would drop it), 10-minute timeout.
- **Table `oauth_handoff_codes`** (Prisma migration `20261120090000_add_oauth_handoff_codes`, appended to the test `schema.sql`): `codeHash` pk, `userId` (cascade), `challenge`, `client`, `expiresAt`. Expired rows are swept on every issue, so no job is needed.
- **`RateLimitFilter`** policies are keyed by method + path now; new: start and callback 20/min/IP (each start creates a session, each callback calls Google), `/auth/handoff` 10/min/IP.
- **Audit events**: OAUTH_REGISTER (detail `google`), OAUTH_REFUSED (`account_exists` / `email_unverified`), OAUTH_FAILURE (Spring's error code, e.g. `access_denied`, `authorization_request_not_found`, `invalid_id_token`), OAUTH_HANDOFF_FAILURE (`unknown_code` / `expired_code` / `bad_verifier`), and LOGIN_SUCCESS with detail `oauth web` / `oauth mobile` when the handoff issues tokens.

## Security checklist

| Item | How it is met | Tested |
|---|---|---|
| `state` entropy and binding | Spring's generator: 32 bytes from `SecureRandom`, base64url. Stored in the server-side session, so bound to the browser by the session cookie; compared on the callback. | callback with a forged state or another sign-in's state fails `authorization_request_not_found` |
| PKCE | S256 forced on (`requireProofKey`); the verifier never leaves the server session. | the verifier Google's token endpoint receives hashes to the challenge sent to Google |
| Nonce and ID token | Spring sends a hashed nonce and checks it in the ID token; the ID token's signature is verified against Google's JWKS, `iss` must be `https://accounts.google.com`, `aud` our client id, `exp`/`iat` current. | every round-trip test verifies a really signed ID token |
| Exact redirect URI | Built from config (`AUTH_ISSUER`), not from the `Host` header; Google rejects any URI not registered in its console. | `redirect_uri` asserted exactly |
| Open redirect | Completion URLs come from config, picked by the `client` enum; no URL is ever taken from the request. | 400 for an unknown `client` |
| Handoff code single-use | 256 random bits; only the SHA-256 is stored; the first redemption attempt deletes it whatever the outcome and must delete exactly one row, so concurrent redemptions cannot both succeed. | reuse and wrong-verifier tests |
| Handoff code binding | Redeeming needs the verifier whose S256 is the challenge the client sent at the start. A leaked code is useless, and an attacker cannot make a victim's browser finish the attacker's sign-in (login CSRF). | wrong verifier spends the code |
| Handoff code lifetime | 60 seconds. | expired-code test |
| Session handling | The start always replaces any earlier session; Spring rotates the session id on authentication; the handler invalidates it on the callback either way. | starting again voids the earlier sign-in |
| Token leakage: storage | Google's tokens are not written to `accounts` and not kept in memory. | `accessToken` null on the created `accounts` row |
| Token leakage: logs | The handler logs only Spring's error code; no tokens, codes or emails reach the logs. Spring's own OAuth logging is at DEBUG/TRACE. | review |
| Token leakage: referrers | `Referrer-Policy: no-referrer` on the callback redirect, so the completion page is not told the callback URL (which carries Google's code). `Cache-Control: no-store` on every redirect and on the token response. | headers asserted on every callback |
| Token leakage: the completion URL | The handoff code is in the completion URL, so it lands in browser history and the web host's request logs. Accepted because of the 60s lifetime, single use and the verifier. The web completion page (1.10) must exchange it at once, strip it from the address bar, and send `Referrer-Policy: no-referrer`. | follow-up |
| Email trust | Requires Google's `email_verified`; an email that already has an account is refused, never linked. | refused-collision and unverified tests |
| Abuse | Start/callback 20/min/IP, handoff 10/min/IP. | review |
| Scope | `openid email profile` only. | asserted |

## Follow-ups

- **Fly staging is always on (2026-11-20)**: the trial org stopped the machine after 5 minutes of running; a card is on file now. Scale-to-zero itself was the deeper problem: a shared CPU runs at a 6.25% baseline once its burst balance (accrued only while running, max 500 s) is spent, so after repeated stop/start cycles a JVM cold start took 4-6+ minutes, Fly's proxy gave up on the waking request after ~8 s, and autostop stopped the machine mid-boot. `fly.toml` now has `auto_stop_machines = "off"`, `min_machines_running = 1` (shared-cpu-1x 512 MB in fra is about $4.30/month, under Fly's $5 waiver for personal orgs). `"suspend"` (memory snapshot, storage-only billing) was the cheaper alternative, but deploys and host maintenance drop the snapshot and fall back to the same throttled cold boot.
- **Web completion page (1.10)**: `/auth/oauth/complete` generates nothing itself. The login button must create the verifier (keep it in `sessionStorage`), start the sign-in with its challenge, and the completion page must exchange `code` + verifier at once, remove `code` from the address bar (`history.replaceState`), send `Referrer-Policy: no-referrer`, and show the `error` values in plain language (`account_exists`: "sign in with your password").
- **Mobile (Phase 3)**: the app's scheme must match `circadium://auth/oauth/complete` (or change `circadium.oauth.mobile-completion-url`). Open the start URL in the system browser (`expo-web-browser` auth session), never a WebView: Google blocks embedded WebViews, and the auth session is what makes the custom-scheme redirect safe.
- **Prod**: add `https://<prod API>/login/oauth2/code/google` to the prod Google client at the web flip (1.10); keep NextAuth's `/api/auth/callback/google` until NextAuth is deleted.
- **More than one instance**: the sign-in session lives in Tomcat's memory, like the rate limiter's buckets. A second instance needs sticky sessions for the two OAuth paths or a shared session store (Spring Session JDBC).
- **Linking Google to an existing password account** (settings → "connect Google", authenticated) is the safe way to give `account_exists` users Google sign-in; not built.
- **Legacy provider tokens** on NextAuth-era `accounts` rows (`access_token`, `id_token`, ...) are unused by Java; null them after the cutover (2.6).
- Microsoft and Apple sign-in (Apple is required by iOS App Store guideline 4.8 once the app offers Google) are planned as [1.10b](1.10b-more-sign-in-providers.md); Meta was evaluated and skipped.
