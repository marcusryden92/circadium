# 1.10 Web auth flip

**Status:** ◐ In progress (2026-11-20) · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** auth client in `client/web`; login/register/reset pages post to Java; `requireUser()` shim — `auth()`'s internals become "verify the Java JWT cookie against the JWKS" (`jose`, edge-safe, so `middleware.ts` gating is unchanged in shape); **all un-migrated server actions keep working through the shim**. OWASP ASVS L1 pass over the whole auth surface. Bake on staging, then prod; **delete NextAuth** (config, adapter, api/auth routes) after a clean week.

**DoD:** production login/2FA/OAuth/reset all on Java; NextAuth gone; a request with no/expired token is rejected on every protected route.

## Decisions (2026-11-20)

- **Hard switch on the branch, no runtime flag.** Prod deploys from `main` and `feature/server` deploys only staging, so the branch is the switch: staging gets Java auth on push, prod at the merge. Rollback is Vercel's instant rollback to the pre-merge deployment (every schema change since `main` is additive, so the old NextAuth build still runs against it). NextAuth is deleted on the branch once the staging bake passes, not after a week in prod.
- **Parts 1-4 are built locally and pushed together.** Every push to `feature/server` deploys staging, and a half-flipped web (reads Java cookies, still logs in through NextAuth) would lock everyone out of staging.
- **`auth()` keeps its name and return shape** (`session.user.{id, name, email, role, isTwoFactorEnabled, isOAuth}`), so the ~25 server actions and route handlers that call it are untouched.
- **The access JWT carries only `sub`, `role`, `sid`**; the shim loads the other fields from Prisma in one query (NextAuth's `jwt` callback already read the user on every call, so no new cost). The DB row is authoritative for `role` too.
- **The shim rejects tokens issued before `passwordChangedAt`** (`iat` second earlier than the change's second; same-second tokens pass). This closes, for the web, 1.7's "access tokens outlive a reset by up to 15 minutes".
- **The JWT `iss` is the API origin** (`NEXT_PUBLIC_API_URL`), as Java's `AUTH_ISSUER` is in every environment; the audience is `circadium-api`.
- **Everyone signed in through NextAuth is signed out once** at the flip (staging on push, prod at merge). Accepted.

## Part 2 build note (2026-11-21)

37 new Jest tests: `refresh.test.ts` (15, fake timers + a Web Locks fake), `client.test.ts` (12), `SessionProvider.test.tsx` (7), `signOut.test.ts` (3). The keeper's three safeguards were mutation-checked: without the Web Lock the two-tab test fails, without the in-lock re-check two tests fail, ignoring a 401 fails one.

- `getSession()` now also returns `accessTokenExpiresAt` (ISO, from the JWT `exp`): the browser cannot read the HttpOnly cookie, so a freshly loaded page learns its refresh time from the server render.
- `lib/session/refresh.ts` (browser): `startSessionKeeper({userId, accessTokenExpiresAt})` refreshes 2 minutes before expiry (wide enough for background-tab timer alignment), and on `visibilitychange`/`online` when within that margin. `refreshSession()` runs under the Web Lock `circadium:session-refresh` and first re-reads the shared state in localStorage (`circadium:session` = `{userId, accessTokenExpiresAt}`), so a tab that waited adopts the other tab's refresh instead of spending the rotated token again (Java would treat that as reuse and revoke the family). 401 → session over (shared state removed, which ends every tab); network/5xx/429 → session kept, retried with backoff 15 s → 5 min. A storage event carrying a different `userId` reports `user-changed`.
- `lib/api/client.ts`: `apiRequest(path, {body, method, authenticated})` with `credentials: 'include'`; errors become `ApiError {status, code, fieldErrors, retryAfterSeconds}` (status 0 + `network_error` when nothing came back). `authenticated` calls run `ensureFreshSession()` first and refresh + retry once on a 401.
- `lib/session/SessionProvider.tsx`: `SessionProvider` (seeded by the server session, so no loading state) + `useSession()` in NextAuth's `{data, status}` shape. Session ended → hard navigation to `/auth/login?callbackUrl=<current path>`; user changed → reload.
- `lib/session/signOut.ts`: `POST /auth/logout`, then tell other tabs, then a full page load. Rejects when the server is unreachable instead of pretending: the cookies would still be live.
- `lib/session/navigation.ts`: session changes are always full page loads, so no Redux store or cached data crosses accounts.

### Part 2 follow-ups

- **Part 4**: the four sign-out buttons must catch `signOut()`'s rejection and show an error. Server actions do not pass through `apiRequest`; the keeper keeps the cookie fresh, but a server action fired in the instant a sleeping tab wakes can still see an expired cookie. Call `ensureFreshSession()` at the start of `useServerAction` and of the sync in `useCalendarServerSync`.
- **Tab closed mid-refresh**: Java rotates the refresh token on receipt; if the tab dies before the browser stores the new cookie, the next refresh presents the old one and the family is revoked (a forced sign-out). Inherent to strict rotation without a grace window. Watch `audit_log` for refresh-reuse events during the staging bake before deciding whether it needs a server-side grace period.

**Found and fixed while doing it.**
- **Refresh vs password change/reset race.**
  - `refresh` locked only the session row. A change or reset running at the same moment waited on that lock, deleted the old row, and missed the replacement row, which had been committed after its delete statement began. So the new refresh token outlived the change.
  - `refresh` now share-locks the user row first (`findByRefreshTokenHashForShare`); both flows update the user row before deleting sessions, so the two run one after the other.
  - `TokenServiceIntegrationTest.refreshWaitsForAPasswordChangeInProgressAndThenFindsItsTokenGone` holds an open `update users` on a raw connection and asserts the refresh waits and then gets `InvalidRefreshTokenException`. Mutation-checked: with the old order it fails ("never waited").
- **Detached `User` saves.**
  - `PasswordResetService` and `EmailVerificationService` loaded the user, did other work (bcrypt for the reset), then saved the stale copy. Saving writes every column, so a web sync committing in between had its `dataVersion` bump rolled back, which weakens the sync's stale-data check.
  - Both now use targeted `UPDATE`s (`updatePassword`, `updateVerifiedEmail`), as the new password change does. The rule is in `server/CLAUDE.md`.

### Findings to fix

1. **The per-IP rate limits can be bypassed (V2.2.1, V11.1.4). Confirmed locally.**
   - `RateLimitFilter` picks its policy by the raw `getRequestURI()`. Spring decodes the path before matching handlers and `PUBLIC_ENDPOINTS`, and its firewall rejects an encoded `/`, `.`, `;` or `%`, but not encoded letters.
   - After `POST /auth/password-reset` reached 429, `/auth/password-r%65set` and `/auth/%70assword-reset` were still accepted (202).
   - Every limited endpoint is affected. The per-email lockout still holds, so one account cannot be brute-forced. What opens up: one IP spraying many accounts, and register/reset mail in bulk.
   - Fix: match policies on the path Spring matches (`PathPatternRequestMatcher`, as `SecurityConfig` does), with a test per encoded variant.
2. **Email change and the 2FA switch need no re-authentication, and nobody is told (V3.7.1, V2.2.3, V2.5.5).**
   - `actions/settings.ts` changes either one on the session alone, and the 2FA switch saves on one click.
   - Takeover path: whoever holds a session (an unlocked laptop, or a copied access token for 15 minutes) changes the email to their own, confirms it, then resets the password. `EmailVerificationService` writes nothing to the old address, so the owner never hears of it.
   - Fix:
     - ask for the current password before an email change or turning 2FA off (password-less accounts: a fresh emailed code);
     - mail the old address after an email change, and the account after 2FA goes off;
     - write an audit row for each.
   - Where: in the web action now, or move both to Java now (planned for Phase 2 Group D). Decision.
3. **The web sends almost no security headers (V14.4.3, 14.4.4, 14.4.6, 14.4.7, 14.3.3).**
   - Prod responses carry only HSTS and `X-Powered-By: Next.js`. `next.config.mjs` sets only `Referrer-Policy` on `/auth/*`.
   - Missing: CSP, `frame-ancestors` / `X-Frame-Options`, `X-Content-Type-Options`, and a site-wide `Referrer-Policy`.
   - Without frame protection any site can frame the settings page, and the one-click 2FA switch (finding 2) is the obvious clickjacking target.
   - Cheap part of the fix: site-wide headers in `next.config.mjs`, `poweredByHeader: false`, and a CSP that only restricts framing and plugins (`frame-ancestors 'none'; base-uri 'self'; object-src 'none'; form-action 'self'`).
   - The part that actually limits XSS is a nonce-based `script-src`. It renders every page dynamically, and `connect-src` must list the API origin, `api.anthropic.com`, Google Maps and anything else the browser calls. Decision: now, or later as its own step.
4. **Any signed-in user can read `/actuator/metrics` and `/actuator/prometheus` (V4.1.3).** Both are exposed and fall under `anyRequest().authenticated()`, and nothing scrapes them (`fly.toml` has no `[metrics]`). Fix: drop them from `management.endpoints.web.exposure.include`, or require `ROLE_ADMIN`.
5. **After sign-out or a password change the access token still works on the server for up to 15 minutes (V3.3.1).**
   - The browser drops the cookie, but a copied token still passes the web shim and Java.
   - Fix: also require the token's `sid` family to still have a `sessions` row.
     - Logout, password change, reset and reuse detection all delete the family's rows.
     - `familyId` is indexed, and on the web the check fits into `getSession()`'s existing user query.
     - In Java it replaces the planned `passwordChangedAt` validator.
   - When: web now, Java before 1.11.
6. **A session in use never expires (V3.3.2).** Every refresh writes `expiresAt = now + 30d`, so an active session lives forever; L1 asks for re-authentication at least every 30 days. Fix: each family gets an absolute end (its start + N days) that rotation cannot extend. Decision on N: 30 meets L1; longer (e.g. 90, for mobile) is a recorded deviation.
7. **Password rules fall short of V2.1 (2.1.1, 2.1.7, 2.1.8, 2.1.12).**
   - New passwords need 8 characters; ASVS 4.0.3 L1 asks for 12 (ASVS 5.0 asks for 8, with 15 recommended).
   - No check against breached passwords. Options: the Have I Been Pwned range API (only the first 5 hex characters of the password's SHA-1 leave the server) or a bundled top-10k list.
   - No strength meter on register, new-password or settings.
   - No show-password toggle on any password field.
   - Decisions: the minimum (12, or 8 recorded as a deviation), and which breach check.
8. **Admin accounts need no second factor (V4.3.1).** The ADMIN-only feedback inspector shows users' consented data snapshots and can impersonate them, yet an ADMIN may have 2FA off. Fix: refuse the admin page and actions unless `isTwoFactorEnabled` (later, whatever stronger factor 1.10b adds).
9. **Data stays in the browser after sign-out (V8.2.3).**

10. **No automated dependency updates (V14.2.1).** Fix: Dependabot for npm (`client/`), Maven (`server/`) and GitHub Actions.
11. **Smaller ones.**

### Decision with a cost either way: cookie name prefixes (V3.4.4)

- `__Host-` is impossible for the access cookie, which needs `Domain` so the web server receives it.
- The refresh cookie can be `__Host-` only with `Path=/`, losing its `/auth` scoping.
- What a prefix buys: a sibling subdomain (staging included, e.g. through an XSS there) can no longer plant a same-named cookie with a more specific path, which the API would read first, signing the victim into the attacker's account.
- Option: `__Host-circadium_refresh` (`Path=/`) and `__Secure-circadium_access`.
- Renaming is cheapest before prod's flip, which signs everyone out anyway. Local keeps unprefixed names (prefixes require `Secure`).

### Accepted as is

- **An emailed code as the second factor (V2.2.2, 2.7.1).** Email is a restricted authenticator; here it is only ever the second factor after a password. Stronger factors belong with 1.10b.
- **bcrypt's 72-byte ceiling (V2.1.2).** 64 characters are allowed only if they are ASCII. Lifting it means pre-hashing, which changes the stored hash format; revisit if the hash algorithm changes.
- **Lockout as a nuisance (V2.2.1).** Anyone who knows an email can keep it locked, up to an hour at a time. A reset and Google sign-in still work, and a reset lifts the lock.
- **Tokens in emailed links (V8.3.1).** A link can only carry its token in the URL.
  - Mitigations: single use, at most 1 hour, `Referrer-Policy: no-referrer`, PostHog masking, and the token reaches Java in a body.
  - Vercel's request logs keep these URLs.
- **Raw link tokens in the database.** Verification, reset and deletion tokens are stored unhashed because the web still reads those tables. Hash them at the 2.6 cutover.
- **Staging receives prod's access cookie (V3.4.5).** `Domain=circadium.app` reaches every subdomain. The staging hosts are ours and read only their own cookie names. The real risk is a subdomain someone else controls (DNS check below).
- **PostHog's scripts without SRI (V10.3.2).** posthog-js loads its recorder from PostHog's CDN through the relay.
- **API JSON without `Content-Disposition` (V14.4.2).** `nosniff` plus `application/json` covers it.

### Passes

- **V2 authentication.**
  - Login is protected by a per-email lockout plus per-IP limits (but see finding 1).
  - Unknown accounts cost the same bcrypt time as real ones, and login, register and reset answer the same whether or not the account exists.
  - Passwords over 72 bytes are refused, never truncated.
  - A password change needs the current password.
  - Paste and password managers work (`autocomplete` set).
  - Reset links: random UUID, 1 hour, single use; a reset ends every session and sends a notice.
  - 2FA codes: 5 minutes, single use. The 2FA step checks the password again, and a wrong code counts toward the lockout.
- **V3 sessions.**
  - Every sign-in starts a new family.
  - Refresh tokens: 256 bits, stored hashed, rotated; a reuse revokes the family.
  - Cookies are HttpOnly, Secure and SameSite (Lax access, Strict refresh). No token in script, URL or `localStorage`.
  - Logout revokes the family and clears both cookies; a password change or reset ends every session (refresh race fixed).
  - Starting Google sign-in invalidates any earlier OAuth session, and the callback ends the new one.
- **V4 access control.**
  - Checks run on the server. The web reads the role from the database, Java from the signed claim.
  - The middleware fails closed (503) when it cannot fetch the keys.
  - Swagger is ADMIN-only outside `local`.
  - Confirming a deletion checks the link belongs to the caller.
- **V5 validation.** Bean Validation on every Java auth request and Zod on the forms; `callbackUrl` same-origin only; OAuth redirects only to the configured completion URLs.
- **V6 / tokens.** RS256 is pinned on both sides (HS256 confusion tested); `iss`, `aud` and `exp` are checked; a `kid` rotation needs no redeploy; `SecureRandom` everywhere.
- **V7 errors and logs.** 5xx bodies are generic with a request id and no stack trace; auth events go to `audit_log`; Sentry runs without `send-default-pii`, so it sends no cookies or auth headers.
- **V8 data.** Token responses are `no-store`; `localStorage` holds only the user id and expiry; export, deletion and `/privacy` exist.
- **V9 transport.** HTTPS is forced (Fly `force_https`, Vercel), with HSTS on both.
- **V13 / V14.5 API.**
  - CORS is an exact allowlist, `null` not accepted, and refusing a foreign `Origin` is the CSRF defence for cookie calls.
  - The API sends Spring Security's headers: `nosniff`, `X-Frame-Options: DENY`, `no-store`, HSTS with `includeSubDomains`.
  - Server actions get Next's own Origin check.
- **OAuth.** PKCE with Google plus our own S256 binding of the handoff code; `state` and nonce; no linking by email; Google's tokens discarded.
