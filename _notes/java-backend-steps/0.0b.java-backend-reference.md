## Technology choices (production-justified)

| Concern | Choice | Why it's the production answer |
|---|---|---|
| Framework | Spring Boot 4.1.x, Java 25 LTS, Maven | Industry standard, longest support horizon, largest hiring pool when the company grows. (Originally planned as Boot 3.x / Java 21; Initializr dropped the 3.x line and 3.5 OSS support is ending, and Java 25 is the newest LTS for maximum support runway — Boot 4.x + Java 25 decided 2026-11-13. Scaffold was generated on Java 21 and is migrating to 25.) |
| Realtime | Plain Spring WebSocket (`TextWebSocketHandler` + per-user session registry) | The protocol is one JSON ping; STOMP adds a broker abstraction with zero payoff at this message volume. Scale path documented (see Production baseline) |
| Background jobs | `@Scheduled` + **ShedLock** (Postgres-backed lock table) from day one | ShedLock makes every job safe under horizontal scaling immediately — no rework when a second instance appears. Quartz only if cron persistence/misfire handling is ever needed |
| Data access | JPA/Hibernate entities (hand-written, `ddl-auto=validate`) + JdbcTemplate for sync/bulk; **Flyway** owns migrations after Prisma cutover | ORM for the 80% CRUD, hand SQL where correctness and batching matter (the OCC transaction) |
| JWT | Spring Security `oauth2-resource-server` validating RS256 via local JWKS; tokens issued with Nimbus JOSE; keypair in secret storage, public key at `/.well-known/jwks.json`, **`kid` header + rotation support from the start** | Asymmetric signing lets Next middleware and any future service verify without sharing a secret |
| Passwords | `BCryptPasswordEncoder` | Wire-compatible with existing bcryptjs `$2a/$2b` hashes — no forced resets at migration |
| OAuth (Google, later Apple) | Authorization-code + **PKCE + `state` + exact-redirect-URI validation**, implemented in `auth/oauth/` against the providers' token endpoints | Full control over the token model (we issue our own tokens, not Spring's session); the security checklist is explicit in item 1.8 and reviewed before production |
| ICS parsing | ical4j | Mature recurrence expansion (overrides, EXDATEs) — port of `parseIcsFeed` |
| Email | Resend REST API via `java.net.http.HttpClient` | Already the product's provider; no SDK needed |
| Google Places/Routes, Google/Microsoft token refresh | plain REST via `HttpClient`, porting `lib/google-maps-api.ts` + `externalSourceServer.ts` (Microsoft's rotating refresh tokens persisted on every fetch) | Same API surface as today |
| Push | Expo Push API (HTTPS POST + receipt checking) | Works with EAS builds; raw FCM/APNs unnecessary |
| API docs | **springdoc-openapi**: OpenAPI 3 at `/v3/api-docs`, Swagger UI at `/swagger-ui.html` (ADMIN-gated in prod) | Living contract documentation; CI exports the spec and `openapi-typescript` type-checks it against the hand-written TS contracts — automatic drift detection |
| Testing | JUnit 5 + **Testcontainers** (Postgres) + the golden contract corpus | Integration tests run against real Postgres in CI, not H2 |
| Observability | Actuator + Micrometer; **Sentry** in both Java and Next; structured JSON logs with request-correlation ids | Non-negotiable for a product with paying users |
| Calendar rendering | **Own**: shared core + one renderer per platform; FullCalendar retired after the web renderer reaches parity (decided 2026-11-22) | The central surface should not depend on an outside maintainer, and a feature should touch one system, not two calendar packages. Every surveyed native package was MIT, so licensing was never the blocker. The mature ones lacked fit or maintenance: calendar-kit had no release since 2025-10, resize undocumented and a poor fit for category windows. The best-fitting one (super-calendar) was 5 months old with one maintainer |
| Native gestures | `react-native-gesture-handler` + `react-native-reanimated` | Drags run on the UI thread. That matters because the engine runs on the JS thread on mobile (no Web Workers in RN). Both are MIT, from Software Mansion, part of Expo's standard stack. `PanResponder` + `Animated` would be zero-dependency but would stutter during regens |

## Calendar (own core + renderers)

**Shape.** Renderers turn platform input into normalized events `{phase, x, y, time}` and draw what the core returns. All decisions live in the core: hit-testing, snap, long-press phases, validation, scope prompts. Tile geometry comes out as `top`/`height` px plus `left`/`width` percentages, and `position: absolute` with `%` works the same in DOM and React Native.

| Truly per-platform | Web | Native |
|---|---|---|
| Pointer input | pointer events | gesture-handler adapter |
| Scroll containers | divs | `ScrollView` / list paging (header + gutter kept in sync) |
| Styling | Vanilla Extract | StyleSheet; tokens need a JS-value source both can read, because `lib/theme/tokens.css.ts` is a Vanilla Extract contract |
| Popovers / modals | Radix | RN Modal / sheets |
| Measurement | not needed: the compact layout comes from duration × hourHeight | same |

```
calendar-core/
  model/        CalendarEvent view model + builders (moved from web/utils/calendar-rendering)
  layout/       visible range (N days, firstDay), day slicing + overnight split,
                time<->px, snap, hit-test (x,y -> day + minute), segment geometry
    placement/  ported FullCalendar overlap algorithm (MIT, attributed)
  interaction/  headless drag state machine: idle -> pending(long-press) -> dragging
                (move | resize-start | resize-end | create) -> commit | cancel;
                live allow/deny hook; preview geometry; auto-scroll speed curve
  edit/         decideEdit -> apply | askScope | reject; pendingEdit override;
                validation (rangeAllowed + windowRangeOverlaps)
  (existing)    eventHandlers, expandTemplateOccurrences, timeWindow, weekStructure, eventTier
```

**Renderer contract.**

| Direction | What passes |
|---|---|
| Renderer gives the core | grid metrics (hourHeight, column widths, scrollTop, visible days), normalized pointer events, the event list |
| Core gives the renderer | positioned segments per column, now-line position, drag preview (geometry + valid flag), and intents: create range, move, resize, ask scope, reject |

Screens route intents to the existing `eventHandlers` apply functions. Everything stays framework-free TS. One optional React hook may live in shared, with `react` as a peer dependency.

**What comes from FullCalendar** (v6.1.21; core/timegrid/interaction/daygrid/rrule all MIT, "Copyright (c) 2021 Adam Shaw"):

| Piece | Where in `client/node_modules/@fullcalendar/` | Treatment |
|---|---|---|
| `SegHierarchy`, `groupIntersectingEntries`, `intersectSpans`, `binarySearch`, `insertAt` | `core/internal-common.js` ~L5850–6080 | **Port to TS**: pure numeric-span code |
| `buildPositioning`, `buildWeb`, `buildNodes`, `findNextLevelSegs`, `stretchWeb`, `webToRects`, `cacheable` | `timegrid/internal.js` L501–636 | **Port to TS**: outputs `{levelCoord, thickness}` fractions = left/width |
| `computeSegVCoords`, `computeFgSegPlacements` | `timegrid/internal.js` L638–683 | Rewrite (~30 lines): FullCalendar measures DOM slats; ours computes from hourHeight |
| Day slicing (`DayTimeColsSlicer`), `buildSlatMetas`, visible range | timegrid + core | Rewrite with date-fns. FullCalendar's versions go through its own date system (`DateEnv`/`DateMarker`) |
| `computeEventMutation`, `computeMutation`, `joinHitsIntoSelection` | `interaction/index.js` L1201, L1523, L1716 | Rewrite, using these as reference (each is a delta between two hits) |
| `PointerDragging`, `ElementMirror`, `AutoScroller`, `ScrollGeomCache`, `OffsetTracker`, `HitDragging` | `interaction/index.js` (~1,000 lines, DOM-bound) | Reference only, for edge cases: touch delay, ignoring the fake mouse events after a touch, cancelling when a touch turns into a scroll, auto-scroll speed |
| Rendering components, option/plugin system, event store, RRule/Luxon plugins | — | Not used. FullCalendar renders through its own Preact; recurrence is already ours |

About 370 lines are ported. They live in one folder, with a header in each file naming FullCalendar and its copyright, and FullCalendar's `LICENSE.md` text beside them.

**Gains over FullCalendar:**
- live validation is a plain function (no DOM writes from `eventAllow`);
- the deferred revert is state, not an imperative `revert()`;
- no connector diffing props, so the identity-stable-options fragility is gone;
- `eventOrder` is our own comparator passed to placement;
- 5-minute snap is a number.

## Risks (ranked)

1. **The sync-transaction port** — the most invariant-dense code in the system (OCC gate, FK order, bulk updates, empty-diff rule). Mitigation: golden corpus + web as first production consumer long before mobile exists.
2. **The web auth flip** (1.10) — the largest single production change. Mitigation: shim keeps all server actions alive; full staging bake; ASVS checklist; NextAuth deleted only after a clean production week.
3. Dual-stack drift during Phase 2. Mitigation: strangler per group, parity test before every delete, Prisma sole migration authority until 2.6.
4. JPA ↔ schema drift during coexistence. Mitigation: `ddl-auto=validate` at startup + golden fixtures + the OpenAPI/contracts CI drift check.
5. **The interaction long tail of the own calendar renderers** (Phase C + 3–4): scroll-vs-drag disambiguation, auto-scroll while dragging, touch on mobile web, Android gesture quirks.

   Mitigation:
   - the headless core is unit-tested with synthetic pointer sequences before any renderer exists;
   - placement parity fixtures against FullCalendar's output;
   - FullCalendar stays the live default behind `?renderer=own` until side-by-side parity.
6. Metro + pnpm workspace linking (`node-linker=hoisted`).
7. Solo bandwidth: Phases 1–2 are each XL. Mitigation: the strangler order lands value incrementally — production WS sync benefits web users long before mobile exists.

## Verification

- **Phase 0**: the gate command per item; prod deploy + manual calendar smoke after 0.1; conformance asserts proven by a deliberate enum rename.
- **Phase 1**: golden corpus green in CI (Testcontainers); e2e login → bootstrap → mutate → sync → forced stale → adoption; two-browser instant adoption on prod; bcrypt back-compat; refresh-reuse revokes the chain; rate limiter and lockout demonstrably trigger; ASVS L1 checklist archived.
- **Phase 2**: per-group parity tests; push reaches a closed app with no duplicates; GDPR export parity; fresh-environment stand-up from Flyway + Java seed.
- **Phase C**: `client/shared` Jest suite covering:
  - placement parity vs FullCalendar fixtures (nested overlaps, equal starts, long + short);
  - overnight split;
  - snap at 5/15 min;
  - hit-test at column and day edges;
  - state-machine sequences.

  Then `/calendar?renderer=own` side by side with FullCalendar on the seeded account. After C.6, `pnpm -r type-check` + the web suite pass with `@fullcalendar/*` gone.
- **Phases 3–7**: the RN plan's verification section (device-vs-web parity per interaction, identical engine output ids, BYOK round-trip, store-track installs), minus its calendar-kit spike. Instead: the native renderer passes the C.4 parity checklist on one iOS and one Android device, plus a ~150-event week staying smooth while a regen runs.
