# 1.4 Error/observability baseline

**Status:** ☑ Done (2026-11-16) · Phase 1 · cross-cutting context in [../java-backend-plan.md](../java-backend-plan.md)

**Task:** `@RestControllerAdvice` → ProblemDetail; Bean Validation wiring; correlation-id filter + structured JSON logging; Micrometer + Actuator metrics; Sentry SDK.

**DoD:** a thrown exception produces a 7807 body, a Sentry event, and a correlated log line.

## Completion note (2026-11-16)

All three DoD artifacts proven by **2 integration tests** (40 total green, `.\mvnw.cmd verify`): a `GET /internal/diagnostics/boom` produces a `application/problem+json` 500 body with `requestId` + `instance`, an `X-Request-Id` response header, a correlated `ERROR` log line, and a Sentry event tagged with `request_id`; a `POST /internal/diagnostics/validate` with a blank `@NotBlank` field produces a 400 ProblemDetail with an `errors` map and zero Sentry events (4xx never reported).

### What was built

**New package `app.circadium.web`** (cross-cutting web-layer infra, deliberate layout addition):

- **`CorrelationIdFilter`** — `OncePerRequestFilter` at `HIGHEST_PRECEDENCE` (before Spring Security); reads/generates `X-Request-Id`, puts it in SLF4J MDC, sets the response header. Inbound ids validated against `[A-Za-z0-9-]{1,64}` to prevent log injection.
- **`GlobalExceptionHandler`** — `@RestControllerAdvice extends ResponseEntityExceptionHandler`. Single funnel via overridden `handleExceptionInternal`: stamps `requestId` + `instance` on every ProblemDetail; 5xx → `log.error` + `Sentry.captureException` (with `request_id` scope tag); 4xx → `log.warn`, no Sentry. Overrides `handleMethodArgumentNotValid` to populate a field-errors map. Adds `@ExceptionHandler(ConstraintViolationException.class)` for `@Validated` params. Catch-all `@ExceptionHandler(Exception.class)` → 500 with generic detail (no stack leak).
- **`DiagnosticsController`** — `@Profile("diagnostics")`, never present in staging/prod. `GET /boom` (throws) + `POST /validate` (Bean Validation probe).

**POM additions** (housekeeping): `micrometer-registry-prometheus` (runtime), `sentry-spring-boot-4-starter:8.64.0` (version-pinned, BOM doesn't manage it), `build-info` goal on the Boot plugin.

**`application.yml` additions**: Actuator exposes `health, info, metrics, prometheus`; health probes enabled (Fly liveness/readiness); common `application` metrics tag; `sentry.*` DSN-optional (empty DSN = disabled, safe for local/CI), per-profile environment, traces off by default; ECS structured JSON console logging on staging/prod (Boot 4 native `logging.structured.format.console: ecs`, no logback.xml).

**Integration test** (`ErrorHandlingIntegrationTest`): `@SpringBootTest` + `@AutoConfigureMockMvc` + Testcontainers; authenticates via `httpBasic` against the default security chain; Sentry enabled with a fake DSN and a `beforeSend` recorder that captures events without network traffic. Proves 7807 shape, correlation-id propagation, Sentry capture on 5xx, and silence on 4xx.

### Design decisions

- **Explicit Sentry capture, not the logback appender.** Sentry's default auto-resolver only reports unhandled exceptions; our advice handles everything, so it would see nothing. Explicit `Sentry.captureException` in the 5xx branch gives precise control. When scheduled jobs land (Phase 2), add `sentry-logback` for non-MVC throws.
- **Boot 4 native structured logging.** `logging.structured.format.console: ecs` auto-includes MDC — zero logback XML.
- **`@AutoConfigureMockMvc` package moved in Boot 4** to `org.springframework.boot.webmvc.test.autoconfigure` (was `org.springframework.boot.test.autoconfigure.web.servlet`). `TestRestTemplate` is not in Boot 4's modular test starters; MockMvc is the standard MVC test tool.

### Follow-up (not blocking)

- The catch-all `@ExceptionHandler(Exception.class)` would wrap a Spring Security `AccessDeniedException` into a 500. Harmless now (no method-security exists), but must rethrow those when `@PreAuthorize` lands in 1.6+.
- Real Sentry dashboard sighting: set `SENTRY_DSN` env locally, run with `local,diagnostics`, hit `/boom` with basic auth, confirm event in dashboard. Same "trivial manual confirm" shape as 1.3's live-Neon check.
