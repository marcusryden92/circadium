# 1.10 Web auth flip

**Status:** ◐ In progress (2026-11-20) · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** auth client in `client/web`; login/register/reset pages post to Java; `requireUser()` shim — `auth()`'s internals become "verify the Java JWT cookie against the JWKS" (`jose`, edge-safe, so `middleware.ts` gating is unchanged in shape); **all un-migrated server actions keep working through the shim**. OWASP ASVS L1 pass over the whole auth surface. Bake on staging, then prod; **delete NextAuth** (config, adapter, api/auth routes) after a clean week.

**DoD:** production login/2FA/OAuth/reset all on Java; NextAuth gone; a request with no/expired token is rejected on every protected route.

## Decisions (2026-11-20)

- **Hard switch on the branch, no runtime flag.** Prod deploys from `main` and `feature/server` deploys only staging, so the branch is the switch: staging gets Java auth on push, prod at the merge. Rollback is Vercel's instant rollback to the pre-merge deployment (every schema change since `main` is additive, so the old NextAuth build still runs against it). NextAuth is deleted on the branch once the staging bake passes, not after a week in prod.
- **Parts 1-4 are built locally and pushed together.** Every push to `feature/server` deploys staging, and a half-flipped web (reads Java cookies, still logs in through NextAuth) would lock everyone out of staging.
- **`auth()` keeps its name and return shape** (`session.user.{id, name, email, role, isTwoFactorEnabled, isOAuth}`), so the ~25 server actions and route handlers that call it are untouched.
- **The access JWT carries only `sub`, `role`, `sid`**; the shim loads the other fields from Prisma in one query (NextAuth's `jwt` callback already read the user on every call, so no new cost). The DB row is authoritative for `role` too.
- **The shim rejects tokens issued before `passwordChangedAt`** (`iat` second earlier than the change's second; same-second tokens pass). This closes, for the web, 1.7's "access tokens outlive a reset by up to 15 minutes".
- **The JWT `iss` is the API origin** (`NEXT_PUBLIC_API_URL`), as Java's `AUTH_ISSUER` is in every environment; the audience is `circadium-api`.
- **Everyone signed in through NextAuth is signed out once** at the flip (staging on push, prod at merge). Accepted.

## Part 2 build note (2026-11-21)

37 new Jest tests: `refresh.test.ts` (15, fake timers + a Web Locks fake), `client.test.ts` (12), `SessionProvider.test.tsx` (7), `signOut.test.ts` (3). The keeper's three safeguards were mutation-checked: without the Web Lock the two-tab test fails, without the in-lock re-check two tests fail, ignoring a 401 fails one.

- `getSession()` now also returns `accessTokenExpiresAt` (ISO, from the JWT `exp`): the browser cannot read the HttpOnly cookie, so a freshly loaded page learns its refresh time from the server render.
- `lib/session/refresh.ts` (browser): `startSessionKeeper({userId, accessTokenExpiresAt})` refreshes 2 minutes before expiry (wide enough for background-tab timer alignment), and on `visibilitychange`/`online` when within that margin. `refreshSession()` runs under the Web Lock `circadium:session-refresh` and first re-reads the shared state in localStorage (`circadium:session` = `{userId, accessTokenExpiresAt}`), so a tab that waited adopts the other tab's refresh instead of spending the rotated token again (Java would treat that as reuse and revoke the family). 401 → session over (shared state removed, which ends every tab); network/5xx/429 → session kept, retried with backoff 15 s → 5 min. A storage event carrying a different `userId` reports `user-changed`.
- `lib/api/client.ts`: `apiRequest(path, {body, method, authenticated})` with `credentials: 'include'`; errors become `ApiError {status, code, fieldErrors, retryAfterSeconds}` (status 0 + `network_error` when nothing came back). `authenticated` calls run `ensureFreshSession()` first and refresh + retry once on a 401.
- `lib/session/SessionProvider.tsx`: `SessionProvider` (seeded by the server session, so no loading state) + `useSession()` in NextAuth's `{data, status}` shape. Session ended → hard navigation to `/auth/login?callbackUrl=<current path>`; user changed → reload.
- `lib/session/signOut.ts`: `POST /auth/logout`, then tell other tabs, then a full page load. Rejects when the server is unreachable instead of pretending: the cookies would still be live.
- `lib/session/navigation.ts`: session changes are always full page loads, so no Redux store or cached data crosses accounts.

### Part 2 follow-ups

- **Part 4**: the four sign-out buttons must catch `signOut()`'s rejection and show an error. Server actions do not pass through `apiRequest`; the keeper keeps the cookie fresh, but a server action fired in the instant a sleeping tab wakes can still see an expired cookie. Call `ensureFreshSession()` at the start of `useServerAction` and of the sync in `useCalendarServerSync`.
- **Tab closed mid-refresh**: Java rotates the refresh token on receipt; if the tab dies before the browser stores the new cookie, the next refresh presents the old one and the family is revoked (a forced sign-out). Inherent to strict rotation without a grace window. Watch `audit_log` for refresh-reuse events during the staging bake before deciding whether it needs a server-side grace period.

**Checks so far.**

- **2, sign out with two tabs:** passes. The other tab followed, and `sessions` was empty afterwards. `audit_log` has `LOGIN_SUCCESS` / `LOGOUT` with the user id and the family.
- **Hydration errors** on the login and landing pages come from the Proton Pass extension: it adds its icon element to the password field and rewrites `<body style>` before React hydrates. They are not ours.

**Decision: the password change moved to Java** and keeps the current browser signed in (ASVS 3.3.3, L2).
- `POST /account/password` (`PasswordChangeService`) takes `{currentPassword, newPassword, client}`.
  - The current password is checked under the login lockout (`PASSWORD_CHANGE_DENIED`, `ACCOUNT_LOCKED`), and accounts without a password get `no_password`.
  - One transaction updates the password, deletes **every** session and starts a new one for the caller, delivered like a login's (cookies for web, body for mobile). Rate-limited as `ACCOUNT_LINK`.
  - After the commit: the `PASSWORD_CHANGED` audit row and the "password changed" email, whose wording now covers both flows ("every device signed in with the old password").
  - The refresh cookie only travels on `/auth/*` paths, so Java identifies the caller from the access token and replaces the session rather than rotating the caller's refresh token.
- Web: `changePassword()` in `lib/api/auth.ts` refreshes the cookie if needed, then sends the request inside `replaceSession()` (`lib/session/refresh.ts`).
  - `replaceSession()` holds the cross-tab refresh lock while the request runs, so no other tab presents the refresh token being revoked (that would 401 and sign the browser out). It then publishes the new expiry to every tab.
  - The settings card stays put and says "Password changed. Other browsers and devices were signed out."
- Removed from the web:
  - the password branch of `actions/settings.ts` (and its writes to `sessions` and `audit_log`);
  - the password fields of `SettingsSchema` (replaced by `PasswordChangeSchema`);
  - the login page's `reason=password-changed` notice.
  - The settings placeholder now says 8 characters.

**Found and fixed while doing it.**
- **Refresh vs password change/reset race.**
  - `refresh` locked only the session row. A change or reset running at the same moment waited on that lock, deleted the old row, and missed the replacement row, which had been committed after its delete statement began. So the new refresh token outlived the change.
  - `refresh` now share-locks the user row first (`findByRefreshTokenHashForShare`); both flows update the user row before deleting sessions, so the two run one after the other.
  - `TokenServiceIntegrationTest.refreshWaitsForAPasswordChangeInProgressAndThenFindsItsTokenGone` holds an open `update users` on a raw connection and asserts the refresh waits and then gets `InvalidRefreshTokenException`. Mutation-checked: with the old order it fails ("never waited").
- **Detached `User` saves.**
  - `PasswordResetService` and `EmailVerificationService` loaded the user, did other work (bcrypt for the reset), then saved the stale copy. Saving writes every column, so a web sync committing in between had its `dataVersion` bump rolled back, which weakens the sync's stale-data check.
  - Both now use targeted `UPDATE`s (`updatePassword`, `updateVerifiedEmail`), as the new password change does. The rule is in `server/CLAUDE.md`.

### Part 5 follow-ups

- **Java itself accepts access tokens issued before `passwordChangedAt`.** Only the web shim refuses them. That has not mattered while Java served only the auth endpoints; once 1.11/1.12 serve app data, add a JWT validator with a per-user `passwordChangedAt` lookup (cached, or kept short by the 15-minute token lifetime).
- **The other interleaving is untested.** The race test covers "change first, refresh second". "Refresh first, change second" is covered by the lock argument (the change's delete starts after the refresh commits and sees its row), not by a test.
- **Lock coupling.** A refresh now waits for any open transaction that has updated the user row, e.g. the web sync bumping `dataVersion`. The wait is at most that transaction's length; watch refresh latency during the staging bake.
