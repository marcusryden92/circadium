# 1.9 Web cookie model

**Status:** ☑ Done (2026-11-20; the in-browser round trip is checked at 1.10's first staging login) · Phase 1 · cross-cutting context in [0.0a.java-backend-plan.md](0.0a.java-backend-plan.md)

**Task:** Java sets `httpOnly; Secure` cookies on the apex (`Domain=.circadium.app`; API at `api.circadium.app`); refresh cookie path-scoped to `/auth/refresh`; CORS with credentials for the web origin. Local dev works because localhost cookies ignore ports.

**DoD:** login from the staging web origin sets cookies usable on a protected API call; CORS blocks a foreign origin.

## Design decisions (2026-11-20)

- **Staging moves to `circadium.app` subdomains.** `vercel.app` and `fly.dev` are both on the Public Suffix List, so no cookie can ever be shared between the old staging hosts. Staging gets the prod layout one level down: web `staging.circadium.app`, API `api.staging.circadium.app`, cookie `Domain=staging.circadium.app` (prod: web `www.circadium.app`, API `api.circadium.app`, `Domain=circadium.app`). Prod's cookies still reach staging hosts (they are subdomains of `circadium.app`), so staging uses its own cookie names (`circadium_staging_*`); the refresh cookie is host-only, so prod's never leaves `api.circadium.app`.
- **Refresh cookie path is `/auth`, not `/auth/refresh`**: logout also needs the refresh token to end the session, and `/auth/refresh` would never be sent to `/auth/logout`.
- **Access cookie SameSite=Lax, refresh cookie Strict.** The access cookie must arrive on a top-level navigation from another site (a link in an email) or the web middleware sees a signed-in user as signed out. Only the web app's own same-site fetches ever need the refresh cookie.
- **Cookie Max-Age = token lifetime.** An expired access cookie disappears instead of lingering. How the web notices "signed in but the access cookie is gone" is 1.10's design (see follow-ups).
- **Web vs mobile is explicit, not guessed from `Origin`.** Login/2FA take `"client":"web"` (default `mobile`, the 1.6 contract). The handoff code already stores the client from the sign-in start. Refresh/logout mirror the channel the token came in on: body → JSON, no body → cookie.
- **Web responses carry no token**, only `accessTokenExpiresAt` / `refreshTokenExpiresAt` (same `TokenResponse` shape, secrets omitted), so the web can refresh ahead of expiry.
- **CORS is the CSRF defence; Spring's CSRF tokens stay off.** Spring's CORS processor 403s every request with a non-allowlisted `Origin`, not just preflights, and browsers send `Origin` on every cross-origin non-GET. That covers sibling subdomains, which SameSite treats as same-site. Requires GETs to stay side-effect free.
- **CORS runs as a servlet filter before the rate limiter**, not inside Spring Security, so 429s and 401s carry the CORS headers and the web can read them (a 429 without `Access-Control-Allow-Origin` looks like a network error to `fetch`).
- **The access cookie is never read on public endpoints.** Spring rejects a request with an invalid token even on `permitAll`, and browsers attach cookies by themselves; a stale access cookie would otherwise 401 the web's own login and refresh calls.
- **Concurrent refreshes (the 1.5 open item):** with one cookie jar shared by all tabs, two tabs refreshing at once would trip reuse detection and log the user out. Resolved on the client: the web serializes refreshes across tabs with the Web Locks API (1.10). No server-side grace window.

### API changes

| Endpoint | Change |
|---|---|
| `POST /auth/login`, `POST /auth/2fa` | optional `client`: `web` → Set-Cookie both, `tokens` has expiries only; `mobile` (default) → unchanged |
| `POST /auth/handoff` | web codes → cookies + expiries; mobile codes → unchanged |
| `POST /auth/refresh` | no body → reads the refresh cookie, answers with cookies + expiries; a failed cookie refresh also clears both cookies. Body → unchanged |
| `POST /auth/logout` | no body → reads the refresh cookie, always 204 and clears both cookies. Body → unchanged |
| every protected endpoint | accepts the access cookie when there is no `Authorization` header |
| every endpoint | CORS: credentials allowed for `circadium.cors.allowed-origins` (default `WEB_BASE_URL`); methods GET/POST/PUT/PATCH/DELETE; request headers `Content-Type`, `X-Request-Id`; exposed `Retry-After`, `X-Request-Id`; preflight cached 1 h; any other `Origin` → 403 |

### What was built

- `auth/AuthCookieProperties` (`circadium.auth.cookies`: names, domain, secure), `auth/AuthCookies` (deliver/clear/read), `auth/ClientType` (was `auth/oauth/OAuthClient`; now also the login `client` field), `auth/CookieBearerTokenResolver`.
- `config/CorsConfig` + `config/CorsProperties`; `SecurityConfig.PUBLIC_ENDPOINTS` (one list for `permitAll` and the resolver).
- Config: `AUTH_COOKIE_DOMAIN` required outside `local`; staging profile overrides the cookie names.

## Follow-ups

- **1.10 web client**: send `client: 'web'` and `credentials: 'include'` on every API call; serialize refreshes across tabs with `navigator.locks.request(...)`; refresh ahead of `accessTokenExpiresAt` while a tab is open, and on 401 once before giving up. The middleware reads the access cookie by its environment's name (`circadium_access` / `circadium_staging_access`, so the web needs it as config) and verifies it against the JWKS. With no access cookie the middleware cannot tell "signed out" from "access cookie expired": send such requests to the login page, which first tries a silent `POST /auth/refresh` and goes on to the requested page if it succeeds.
- **Vercel staging `NEXT_PUBLIC_APP_URL`** is still `https://circadium-staging.vercel.app`; change it to `https://staging.circadium.app` and redeploy the staging web in 1.10 (the web's own emailed links and calendar-connect redirect should use the new host).
- **Prod (1.10)**: `api.circadium.app` DNS + Fly cert for the prod app, `AUTH_COOKIE_DOMAIN=circadium.app`, `WEB_BASE_URL=https://www.circadium.app` (the apex 308s to `www`, so `www` is the only web origin CORS needs).
- `__Secure-` cookie name prefixes (browsers then refuse the cookie unless it is Secure and set over HTTPS) would harden the deployed names; skipped because local runs on plain HTTP and the names would differ per environment anyway.
- Mobile clients never send `Origin`, so CORS never applies to them; if a mobile WebView ever calls the API, it is a foreign origin and gets 403.
